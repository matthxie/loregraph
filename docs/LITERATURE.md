## Graphify — Open-Source Knowledge Graph Skill for AI Coding Assistants (graphify.net, YC S26)

**Source:** `graphify` — <https://graphify.net/#architecture>  
**TL;DR:** A local-first tool that turns a whole codebase (plus its docs, PDFs, images, and video transcripts) into a persistent NetworkX knowledge graph an LLM answers questions by traversing, not by vector similarity.

**Problem addressed.** It targets the cost and incoherence of feeding raw files (or vector-retrieved chunks) to an LLM over a large, multi-modal corpus. Chunk-and-embed RAG loses structural relationships (call graphs, "this table -> this handler -> this component") and burns tokens; Graphify builds an explicit entity/relationship graph so a single query can trace a path across the whole project and return only the minimal relevant subgraph, claiming ~71.5x fewer tokens per query than reading raw files.

**Core method.** A two/three-pass pipeline mixes deterministic and LLM extraction. Pass 1: tree-sitter parses 19-33 languages locally with zero LLM calls, emitting an AST from which classes, functions, imports, call graphs, docstrings, and rationale comments become nodes/edges. Pass 2 (media): faster-whisper (local CTranslate2 Whisper) transcribes audio/video. Pass 3: parallel Claude subagents do semantic extraction on non-code content — Markdown/PDFs (with citation mining) and images (via Claude Vision) — emitting concepts and relationships. Everything merges into one NetworkX graph, persisted as graph.json with a SHA256-based file cache so only changed files reprocess; Leiden community detection (via graspologic) clusters nodes into "neighborhoods" using graph topology alone — no embeddings, no vector store. Retrieval is BFS/DFS traversal that extracts the minimal subgraph answering a query.

**Techniques.**
- Tree-sitter AST extraction (deterministic, local, no LLM, 19-33 languages)
- LLM semantic extraction via parallel Claude subagents for docs/PDF/images
- Claude Vision for image/diagram ingestion; faster-whisper for A/V transcription
- NetworkX in-memory graph persisted to graph.json
- Leiden community detection via graspologic (connected-community guarantee over Louvain)
- Edge confidence tagging: EXTRACTED (1.0), INFERRED (0-1.0), AMBIGUOUS (human review)
- Hyperedges grouping 3+ nodes; semantically_similar_to relationship type
- BFS/DFS subgraph traversal as the retrieval mechanism (no vector similarity)
- SHA256 content-hash cache for incremental rebuilds; git-hook auto-rebuild on commit

**Relevance to this project.** Directly relevant and partly contrarian. (1) Tag/entity graph: Graphify is entity-and-relationship based, and validates the user's plan to extract entities/concepts from LLM summaries, but it adds a crucial idea the user lacks — provenance tagging on EDGES (EXTRACTED vs INFERRED vs AMBIGUOUS with confidence), not just tags on nodes. The user should consider confidence/source labels on extracted relationships. (2) Embeddings on tags vs summaries vs chunks: This is the sharpest challenge. Graphify deliberately uses NO embeddings and NO vector store — Leiden clusters on topology and retrieval is pure graph traversal. The user's plan to embed tags/summaries for fast search is the opposite bet. The lesson is not to abandon embeddings but to treat traversal as primary and embeddings only as an entry-point index into the graph (find a seed node, then traverse) rather than the main retrieval path. (3) Traversal: Graphify's BFS/DFS-returns-minimal-subgraph strongly validates the user's LLM-traversable, bidirectional design and the "seen" flag — BFS over a bidirectional graph needs exactly that visited-set semantics, so the per-node seen flag with bulk-clear is the right primitive. (4) Dedup/normalization: Graphify relies on deterministic AST identity (stable symbol names) for code, so it largely sidesteps the user's "tag drift" problem; for LLM-extracted concepts it offers a semantically_similar_to edge rather than collapsing duplicates. This suggests an alternative to the user's hash-table tag normalization: instead of (or in addition to) forcing tags into a canonical form, keep near-duplicates as distinct nodes linked by similarity edges and let community detection group them. (5) Multimodal: Graphify validates the photos/files path exactly — Claude Vision for images, PDF citation mining, Whisper for media — confirming the user's "LLM summarizes each object then extract tags" approach generalizes across modalities.

**Pitfalls / limitations.**
- No embeddings/vector store means weak fuzzy/semantic recall: if the query vocabulary doesn't match extracted entity/tag names, traversal has no good entry point — a pure-traversal design can miss things a similarity search would catch.
- LLM-extracted edges (INFERRED) carry hallucination risk; the confidence tag surfaces but does not fix this, and AMBIGUOUS edges assume a human-review loop that an autonomous system won't have.
- Concept dedup is unsolved — relying on semantically_similar_to instead of merging can let near-duplicate concept nodes proliferate (the exact 'tag drift' the user fears), shifting the problem to clustering quality.
- Graphify's efficiency wins lean heavily on deterministic AST identity for code; Wikipedia articles have no AST, so the user's corpus falls entirely into the noisier LLM-extraction path where entity identity/normalization is hard.
- graph.json + NetworkX is in-memory single-process; fine for ~100 articles but not a concurrent/scalable graph DB.
- The 71.5x token claim is vendor-reported on mixed code corpora and may not transfer to text-only Wikipedia.

**Key takeaways.**
- Make traversal the primary retrieval path and demote embeddings to an entry-point index: embed tags/summaries only to find seed nodes, then BFS/DFS the bidirectional graph from there.
- Tag the EDGES, not just nodes — record provenance (extracted vs inferred) and a confidence score so the LLM can weight or discard low-confidence relationships during traversal.
- Reconsider hard tag normalization: a 'semantically_similar_to' edge plus community detection (Leiden) can group near-duplicate tags without a brittle canonical hash table — or combine both.
- Your per-node 'seen' flag with bulk-clear is the correct visited-set primitive for BFS over a bidirectional graph — Graphify's design confirms traversal-first retrieval needs exactly this.
- Use deterministic structure where it exists and reserve the LLM for the genuinely unstructured parts; for Wikipedia, lean on hyperlinks/infoboxes/categories as deterministic edges to reduce reliance on noisy LLM-inferred relationships.
- Add an incremental content-hash cache (SHA256 per object) so re-ingesting the 100-article test set only reprocesses changed inputs.
- Support hyperedges (relationships spanning 3+ nodes) for concepts that aren't naturally pairwise.

## From Local to Global: A Graph RAG Approach to Query-Focused Summarization (Edge et al., Microsoft Research, 2024)

**Source:** `graphrag-ms` — <https://arxiv.org/abs/2404.16130>  
**TL;DR:** Builds an LLM-extracted entity-relationship knowledge graph, partitions it into a hierarchy of communities via Leiden, pre-generates community summaries, and answers corpus-wide "global sensemaking" questions by map-reduce over those summaries.

**Problem addressed.** Conventional vector RAG retrieves a handful of locally-similar chunks, which fails on global/corpus-level questions ("what are the main themes across the whole dataset?") because the answer isn't localized in any few chunks. Query-focused summarization handles such questions but doesn't scale to RAG-sized corpora (~1M+ tokens). GraphRAG bridges the two: it pre-indexes the corpus into a graph + hierarchical community summaries so global questions can be answered without stuffing the whole corpus into context.

**Core method.** Source text is split into chunks; an LLM extracts typed entities (name, type, description) and relationships per chunk, using "gleaning" self-reflection rounds (logit-biased yes/no for "did you miss entities?") to recover recall lost at larger chunk sizes. Extracted instances are aggregated into a graph where duplicate relationships become edge weights, and per-node/edge descriptions are LLM-summarized. Leiden community detection is applied recursively to produce a multi-level hierarchy (C0 root coarse communities down to C3 leaf communities), each level being a mutually-exclusive, collectively-exhaustive partition. Each community gets a pre-generated summary, built by adding element summaries in decreasing order of combined node degree until the context window fills (higher levels substitute shorter sub-community summaries when they overflow). At query time, community summaries are shuffled and chunked, mapped in parallel to partial answers each scored 0-100 for helpfulness, then the highest-scored partials are concatenated and reduced into one global answer.

**Techniques.**
- LLM entity+relationship extraction with typed schema and few-shot domain tuning
- Gleaning / self-reflection multi-round extraction with logit bias to boost recall at large chunk sizes
- Aggregation of duplicate relations into edge weights; exact-string entity matching (dedup tolerated via clustering)
- Leiden hierarchical community detection (recursive, MECE partitions per level)
- Degree-prioritized community summarization to fit context window
- Hierarchical summary substitution (sub-community summaries replace element summaries when overflowing)
- Map-reduce over shuffled community-summary chunks with 0-100 helpfulness scoring and filtering
- LLM-as-judge head-to-head evaluation on comprehensiveness/diversity/empowerment with directness as control
- Claimify claim-extraction + agglomerative clustering (1-ROUGE-L) for objective diversity/comprehensiveness metrics

**Relevance to this project.** Strongly validates the core pipeline shape: ingest -> LLM-summarize each object -> extract structured nodes -> build graph. CHALLENGES the tag-centric design: GraphRAG's nodes are typed entities with rich text descriptions and weighted relationships, not bare tags. Tags alone lose the relational/edge information that makes graph traversal useful; the user should treat tags as one node attribute and also extract entity nodes + typed edges. VALIDATES the dedup/hash-table-for-tag-drift concern but reframes it: GraphRAG uses exact-string matching plus the observation that near-duplicates get co-clustered during community summarization, so perfect normalization is less critical than the user fears - the summarization/clustering step is forgiving. On EMBEDDINGS: GraphRAG does NOT embed tags for primary retrieval; for global queries it bypasses embeddings entirely and uses pre-computed community summaries via map-reduce. This challenges "embed on tags for fast search" as the main retrieval path - it works for local lookups but not for whole-corpus questions. The user should consider embedding summaries (richer than tags) and adding a community-summary layer for breadth queries. On TRAVERSAL: the user's LLM-walks-the-graph-with-a-seen-flag idea is closest to "local" traversal; GraphRAG argues pure local traversal misses global structure, and offers hierarchical community summaries as a precomputed alternative to live walking - relevant since live LLM traversal over 100 Wikipedia articles is token-expensive and may not surface cross-article themes. The bidirectional graph aligns with GraphRAG's undirected, degree-weighted edges. The ~100 Wikipedia articles test set is well-matched to GraphRAG's news/podcast scale (15k-20k edges). MULTIMODAL: GraphRAG is text-only - it offers no guidance for the user's photos/images, so image handling (caption-then-extract) is the user's own extension, not covered here.

**Pitfalls / limitations.**
- Indexing is expensive and slow: ~281 minutes and many GPT-4 calls to index a single podcast dataset; full hierarchy (C3) costs ~750k-1.1M context tokens to build summaries vs ~27k-40k for root level (C0)
- Entity matching is naive exact-string; relies on downstream clustering to absorb duplicates - can still fragment if surface forms diverge widely (the user's tag-drift worry is real here)
- Pre-built community summaries go stale on every corpus update; incremental re-indexing of Leiden communities is non-trivial
- No native multimodal/image support
- Global map-reduce issues many parallel LLM calls per query (one per summary chunk) - query-time cost and latency, not just index cost
- Evaluation is LLM-as-judge on win-rates, not ground-truth accuracy; risk of length/verbosity bias (mitigated only by a 'directness' control)
- Best results came from small 8k context chunks during reduce, and root-level C0 summaries - i.e. more graph depth did not monotonically help, so the expensive deep hierarchy may be wasted for many queries

**Key takeaways.**
- Extract typed entities + weighted relationships, not just flat tags - the edges are what make a graph worth traversing; keep tags as an attribute layer on top of entity nodes.
- Add a precomputed community-summary layer (cluster the graph, summarize clusters) so the LLM can answer broad cross-document questions without live-walking every node - cheaper and better than per-query traversal for global queries.
- Don't over-engineer tag normalization: a clustering/summarization step absorbs near-duplicate entities, so the hash-table dedup is a nice-to-have, not load-bearing - spend effort on extraction recall instead.
- Use gleaning (a second 'did you miss anything?' LLM pass) to keep extraction recall high while using larger chunks, cutting LLM-call count and cost.
- Embed summaries rather than bare tags for richer semantic retrieval, and recognize embeddings alone won't serve whole-corpus questions - pair them with the community-summary map-reduce path.
- Budget for indexing cost up front and prefer coarse (root-level) community summaries first; deeper hierarchy levels add large token cost for diminishing query-quality gains.
- Evaluate with comprehensiveness/diversity LLM-judge comparisons plus a directness control to catch verbosity bias - directly reusable for the user's 100-article test set.

## HippoRAG: Neurobiologically Inspired Long-Term Memory for Large Language Models (Gutiérrez et al., NeurIPS 2024)

**Source:** `hipporag` — <https://arxiv.org/abs/2405.14831>  
**TL;DR:** Builds a schemaless LLM-extracted entity knowledge graph (a "hippocampal index") over a corpus and answers multi-hop queries in a single retrieval step by seeding Personalized PageRank with query entities, replacing iterative retrieve-read loops.

**Problem addressed.** Standard RAG encodes each passage in isolation, so it cannot integrate knowledge across passage boundaries. Multi-hop questions where the answer requires associating facts that never co-occur in one chunk force expensive iterative retrieve-generate loops (e.g. IRCoT), and even those fail on "path-finding" questions where many candidate paths exist. HippoRAG targets cross-passage knowledge integration and single-step multi-hop retrieval.

**Core method.** Offline, an instruction-tuned LLM (GPT-3.5) runs OpenIE on each passage in two steps (first NER, then triple extraction seeded with those entities) to produce (subject, relation, object) triples, which are merged into one corpus-wide schemaless KG whose nodes are noun phrases. A retrieval encoder (Contriever or ColBERTv2) adds "synonymy" edges between any two nodes whose embedding cosine similarity exceeds a threshold tau (0.8), softening tag/entity drift. A node-to-passage matrix P records which passages each node came from. Online, the LLM extracts named entities from the query, the encoder links each to its nearest KG node (these become seed "query nodes" with equal probability mass), and Personalized PageRank (damping 0.5) diffuses probability over the KG so relevant neighbors light up in a single step. Seed probabilities are first scaled by node specificity s_i = 1/|P_i| (an IDF-like local signal: nodes in fewer passages count more), then the resulting node distribution is multiplied by P to rank passages.

**Techniques.**
- Two-stage LLM OpenIE (NER then triple extraction) for KG construction
- Schemaless entity/noun-phrase knowledge graph built corpus-wide
- Synonymy edges via retrieval-encoder cosine similarity above threshold tau=0.8 (node resolution / dedup)
- Personalized PageRank seeded at query-entity nodes for single-step multi-hop
- Node specificity (1/passage-count, IDF surrogate) reweighting PPR seeds
- Encoder-based query-entity-to-node linking (argmax cosine)
- Node-to-passage matrix multiply to convert node scores into passage ranking
- Ensembling/combination with IRCoT for further multi-step gains

**Relevance to this project.** Strongly validates several of the user's choices and sharpens others. (1) Tag/entity-based graph: HippoRAG confirms an LLM-extracted entity graph beats chunk-embedding RAG on cross-document reasoning, supporting tags-as-nodes. But its nodes are extracted ENTITIES (noun phrases from triples) with real typed relations, not free-form summary tags; the ablation shows GPT-3.5 producing general-concept triples (2x more than REBEL) is what makes it work, so tags should carry relational/conceptual richness, not just topic labels. (2) Tag-drift hash table: HippoRAG addresses the exact same synonymy/node-resolution problem but via embedding-similarity EDGES rather than a normalizing hash table -- it does NOT collapse near-duplicates into one node, it links them and lets PPR flow across. This is a concrete improvement to consider: a hard hash-normalize can over-merge; soft synonymy edges preserve nuance and are tunable via tau. Ablation shows synonymy edges matter most when relevant concepts are named entities. (3) Embedding on tags vs summaries vs chunks: HippoRAG embeds the SHORT NODE STRINGS (entities/phrases) for both linking and synonymy, validating the user's tag-embedding instinct over chunk embeddings for the graph layer -- summaries are not embedded at all. (4) Traversal strategy: the biggest lesson. The user's plan has an LLM walk the graph hop-by-hop with a per-node "seen" flag. HippoRAG argues the opposite -- replace iterative/LLM traversal with one PPR diffusion from seed nodes, 10-30x cheaper and 6-13x faster while matching iterative quality, and an ablation shows naive 1-hop neighbor expansion actually HURTS vs PPR. Consider PPR (or another graph-diffusion ranker) as the core retrieval primitive and reserve LLM traversal/seen-flags for debug or path-finding. (5) Bidirectional graph: compatible -- PPR runs over an undirected/bidirectional edge set (triples + synonymy), so the bidirectional design fits naturally. (6) Node specificity / IDF: a cheap valuable add the user's plan lacks -- weight nodes by inverse passage-frequency to downrank generic tags. (7) Multimodal: HippoRAG is text-only and offers NO guidance on image ingestion -- images would need a VLM to emit text triples/tags before entering this pipeline.

**Pitfalls / limitations.**
- Text-only: no multimodal/image handling -- images must be captioned/triple-extracted upstream before entering the graph
- All components are off-the-shelf and untrained; error analysis attributes most failures to NER and OpenIE extraction quality
- OpenIE consistency degrades on longer documents (Wikipedia articles can be long -- relevant to the ~100-article test set)
- Scalability beyond benchmark size (a few thousand passages) is explicitly unvalidated; PPR and synonymy over a very large node set may become costly
- Synonymy is purely embedding-cosine with a fixed threshold -- no aggressive normalization, so true duplicates can stay split or false synonyms can link if tau is off
- Weaker on HotpotQA due to a concept-context tradeoff; gains are largest on entity-centric data (2WikiMultiHopQA)
- Open-weight LLMs (Llama-3.1-8B) drop notably on some datasets vs GPT-3.5 for triple extraction; KG quality is LLM-dependent
- PPR is a flat diffusion ranker -- it does not use relation semantics to guide traversal (noted as future work)

**Key takeaways.**
- Prefer a graph-diffusion ranker (Personalized PageRank) seeded at query-entity nodes over LLM hop-by-hop traversal for the default retrieval path -- far cheaper/faster, does single-step multi-hop, and naive neighbor expansion measurably hurt their results.
- For tag drift, consider soft synonymy EDGES via embedding cosine + threshold instead of (or alongside) a hard normalizing hash table, so near-duplicate tags stay distinct but connected and tunable.
- Add node specificity (inverse passage-frequency, an IDF surrogate) as a seed reweighting -- a cheap signal that downranks generic tags and improved retrieval in their ablations.
- Embed the short node strings (tags/entities) for linking and dedup, as planned; ensure extracted tags carry relational/conceptual richness (typed relations), not just topic labels, since extraction quality drives everything.
- For the Wikipedia test set, watch OpenIE/extraction quality on long articles and budget for it as the dominant error source; for images, run a VLM to emit text tags/triples before ingestion since this method gives no native multimodal path.

## A-MEM: Agentic Memory for LLM Agents

**Source:** `p-2502` — <https://arxiv.org/abs/2502.12110>  
**TL;DR:** A Zettelkasten-inspired agentic memory system where each stored item becomes an LLM-authored "note" (content + contextual description + keywords + tags), then is auto-linked to semantically similar existing notes and triggers evolution (rewriting) of those neighbors' tags/context.

**Problem addressed.** LLM-agent long-term memory systems are either flat vector stores (no structure) or rigid hand-built graph DBs with fixed schemas and operations that don't adapt across tasks. A-MEM targets the problem of building an interconnected, self-organizing memory network that grows and reorganizes itself as new information arrives, without a predefined ontology — directly the "how do I structure a knowledge graph an LLM can traverse" problem the user faces.

**Core method.** For each new memory the LLM generates a structured "note": the raw content plus an LLM-written contextual description, a set of keywords, and tags (Zettelkasten-style atomic note). The note's text is embedded (default all-MiniLM-L6-v2) and stored in ChromaDB; the graph of typed links between notes is held separately (e.g. NetworkX in community ports). Link generation is two-stage: retrieve top-k nearest neighbors by embedding similarity, then let the LLM decide which of those candidates genuinely warrant a link and why — so edges are LLM-judged, not raw cosine thresholds. Critically, adding a note triggers "memory evolution": the new note can cause the LLM to rewrite the contextual descriptions and tags of its linked historical neighbors, so the network continuously re-organizes rather than being append-only. Retrieval at query time is embedding similarity over the notes plus traversal of the established links.

**Techniques.**
- LLM-authored structured notes (content + context + keywords + tags)
- Two-stage link generation: k-NN retrieval then LLM relevance judgment
- Memory evolution: new notes trigger LLM rewrites of neighbors' tags/context
- Dual storage: ChromaDB vector index + explicit typed-edge graph (NetworkX)
- Sentence-transformer embeddings (all-MiniLM-L6-v2) over note text
- Zettelkasten atomic-note + interlinking design pattern
- Hybrid retrieval: semantic similarity + graph link traversal

**Relevance to this project.** Strong validation of the user's overall shape: LLM-summarize-each-object then extract tags/keywords is exactly A-MEM's note construction, and embedding for fast search plus a linked graph mirrors the user's plan. Specific lessons: (1) Tag-based design is endorsed — A-MEM treats tags/keywords as first-class structured attributes, but it does NOT embed tags in isolation; it embeds the richer note text (content + context), suggesting the user should embed summaries (or summary+tags concatenated) rather than tags alone, since bare-tag embeddings lose disambiguating context. (2) Edge creation: A-MEM does not blindly connect by cosine similarity — it uses k-NN as a candidate filter then an LLM gate to decide real links. This is a concrete, better traversal/edge strategy than pure embedding edges, and pairs naturally with the user's bidirectional graph (links are mutual). (3) Memory evolution challenges the user's plan in a useful way: A-MEM actively rewrites old nodes' tags when new ones arrive — this is a principled answer to "tag drift." Instead of (or in addition to) a hash-table normalizer, the LLM can re-harmonize neighbor tags at insert time. The user's hash-table dedup is still complementary (cheap exact/near-duplicate collapse) but A-MEM shows the semantic-consolidation half. (4) Traversal: A-MEM's retrieval is similarity-seed + link-hop, validating the user's LLM-traversal-with-seen-flag idea; the "seen" flag maps onto bounded graph walks over evolved links. (5) Gap: A-MEM is essentially unimodal text — it offers no image handling, so the user's photo/multimodal ingestion (caption-then-treat-as-text) is an extension beyond this paper, not something it solves.

**Pitfalls / limitations.**
- Memory evolution rewrites existing notes' tags/context on every insert — at ~100 articles this is cheap, but it is O(k) LLM calls per insertion and re-embedding of mutated neighbors, which scales poorly and can cause non-deterministic drift of older nodes.
- No tag normalization / hash-table dedup in the original design — tags are free-form LLM output, so near-duplicate tags ('NLP' vs 'natural language processing') will accumulate unless you add exactly the normalization layer the user already plans.
- Embeds note text, not tags alone; if you embed only tags expecting A-MEM-level retrieval quality you will underperform what the paper actually does.
- Link quality depends on the LLM gate; a weak/cheap model produces noisy or missing edges, and the paper's gains vary across the six foundation models tested.
- Evaluated on conversational memory (LoCoMo-style long dialogue QA), not Wikipedia-scale encyclopedic knowledge or multimodal corpora — transfer to the user's 100-article image+text benchmark is unverified.
- No multimodal support; images must be externally captioned before they enter the note pipeline.

**Key takeaways.**
- Embed the summary/context (optionally summary+tags), not tags in isolation — bare-tag embeddings drop the disambiguating context A-MEM relies on.
- Gate edges with the LLM: use vector k-NN only to propose candidate neighbors, then have the LLM confirm and type each link; combine with your bidirectional storage so confirmed links are mutual.
- Adopt 'memory evolution' as a semantic anti-drift mechanism: on insert, let the LLM re-harmonize neighbors' tags. Keep your hash-table normalizer as the cheap exact/near-dup layer; the two are complementary, not redundant.
- Make notes structured and atomic (content + LLM context description + keywords + tags) — this is the unit that both embeds well and traverses well.
- Budget for insertion cost: evolution + re-embedding makes writes expensive; consider batching evolution or capping neighbor rewrites, especially before scaling past your 100-article test.
- Plan multimodal yourself: caption images into the note text up front, since A-MEM gives no native image path.

## RAPTOR: Recursive Abstractive Processing for Tree-Organized Retrieval (Sarthi et al., ICLR 2024)

**Source:** `raptor` — <https://arxiv.org/abs/2401.18059>  
**TL;DR:** Builds a multi-level summarization tree by recursively clustering and abstracting text chunks, then retrieves across all abstraction levels at once so an LLM can pull both fine detail and big-picture context for a query.

**Problem addressed.** Classic chunk-based RAG retrieves short contiguous passages and fails on questions that require integrating information spread across a long document or reasoning over its overall themes. Flat top-k chunk retrieval has no notion of higher-level abstraction, so multi-hop and thematic ("what is this document about / how do these parts relate") questions are poorly served. RAPTOR adds a hierarchy of summaries so retrieval can match a query at whatever granularity it needs.

**Core method.** Text is split into ~100-token chunks (respecting sentence boundaries) and embedded with SBERT (multi-qa-mpnet-base-cos-v1) as leaf nodes. These embeddings are soft-clustered: UMAP reduces dimensionality (varying its n_neighbors to first find global clusters, then local sub-clusters), and a Gaussian Mixture Model with cluster count chosen by BIC assigns each node to one or more clusters (soft membership, so a chunk can live in multiple topical clusters). Each cluster's member texts are concatenated and summarized by an LLM (gpt-3.5-turbo, prompt "Write a summary of the following, including as many key details as possible"); the summary is re-embedded and becomes a parent node one level up. This cluster-summarize-embed step recurses bottom-up until nodes collapse to a single root or further clustering is infeasible. At query time, the best strategy is the "collapsed tree": all nodes from every layer are flattened into one pool and ranked by cosine similarity to the query, greedily filling a token budget (~2000 tokens, ~20 nodes) regardless of level — this beats layer-by-layer top-k tree traversal because it lets the retriever pick the right granularity per query instead of committing to a level.

**Techniques.**
- 100-token chunking with sentence-boundary preservation
- SBERT (multi-qa-mpnet-base-cos-v1) embeddings for both chunks and summaries
- UMAP dimensionality reduction with varied n_neighbors for global-then-local hierarchical clustering
- Gaussian Mixture Model soft clustering (nodes can belong to multiple clusters)
- BIC for automatic cluster-count selection
- Recursive re-clustering when a cluster exceeds the summarization token limit
- LLM abstractive summarization (gpt-3.5-turbo) to build parent nodes
- Bottom-up recursion until single root
- Collapsed-tree retrieval: flatten all layers, cosine rank, greedy fill to ~2000-token budget
- Tree-traversal retrieval (top-k per layer) as the inferior alternative

**Relevance to this project.** Strongly relevant and partly a competing design. (1) Validates the core bet of the user's project — that an LLM-traversable store should expose information at multiple abstraction levels, and that LLM-generated summaries are good retrieval surfaces. The user's per-object summary step is exactly RAPTOR's leaf-summarization, and RAPTOR proves summaries cluster and retrieve well. (2) Embedding choice: RAPTOR embeds full summaries (and raw chunks), NOT tags. This challenges the user's plan to embed primarily on tags — tags are lossy and may underperform dense summary embeddings for semantic match; the safer choice is to embed summaries (and optionally chunks) and use tags as a complementary symbolic/filtering index, not the primary vector. (3) Traversal: RAPTOR's headline finding — collapsed-tree (flat similarity over all nodes) beats hierarchical layer-by-layer traversal — is a direct caution against an LLM walking the graph level-by-level following the 'seen' flag. A flat vector pre-filter that surfaces candidate nodes at any level, with the LLM then traversing bidirectional edges only locally, will likely outperform pure stepwise graph walking. The 'seen' flag and bulk-clear remain useful for cycle avoidance during whatever local expansion the LLM does. (4) Structure: RAPTOR's hierarchy is DERIVED automatically by clustering, whereas the user's graph edges come from extracted tags/entities. RAPTOR suggests adding an automatically-built summary/cluster layer ON TOP of the tag graph would help thematic queries that tag co-occurrence alone misses — i.e. tag-based graph and abstraction-tree are complementary, not either/or. (5) Dedup/normalization: RAPTOR has no equivalent to the user's tag-normalization hash table; its soft clustering implicitly groups near-duplicate content but never canonicalizes labels, so the user's anti-tag-drift mechanism is a genuine addition RAPTOR lacks. (6) Multimodal: RAPTOR is text-only — it offers no guidance for the user's image handling; images must be captioned/summarized into text first to enter a RAPTOR-style pipeline, which aligns with the user's plan to LLM-summarize photos into text before tagging/embedding.

**Pitfalls / limitations.**
- ~4% of generated summaries contained minor hallucinations (paper reports these did not propagate upward, but in a persistent graph they could ossify as facts)
- Tree-building cost scales with LLM summarization calls — every cluster at every level is an API call, expensive for large or frequently-updated corpora
- Designed as a build-once index over a fixed corpus; incremental updates/insertions are not addressed, awkward for a continuously-growing input store
- GMM's Gaussian assumption and UMAP reduction may not fit text-embedding manifolds well, and UMAP is stochastic so trees are not fully reproducible
- Soft clustering duplicates content into multiple parents, inflating storage and the candidate pool
- Collapsed-tree retrieval re-scores every node per query — cost grows with total node count unless an ANN index is maintained over all levels
- Text-only; no native multimodal path

**Key takeaways.**
- Embed summaries (and/or raw chunks), not just tags — RAPTOR's retrieval surface is dense summary embeddings; treat your tags as a symbolic filter/index layered on top, not the primary vector.
- Prefer flat similarity retrieval over the whole node set ('collapsed tree') to a single LLM-driven level-by-level walk; let a vector pre-filter pick candidates at any abstraction level, then have the LLM traverse edges locally.
- Add an automatically-derived abstraction/summary layer above the tag graph — recursive cluster-then-summarize captures thematic structure that tag co-occurrence edges miss.
- Keep summaries source-linked and consider a verification pass: ~4% hallucination at build time becomes permanent error in a stored graph.
- Multimodal must be reduced to text first (caption/summarize images) before clustering/embedding — consistent with the plan, but it means image semantics are only as good as the captioner.
- Your tag-normalization hash table is a real gap in RAPTOR worth keeping — soft clustering groups content but never canonicalizes labels.

## TnT-LLM: Text Mining at Scale with Large Language Models

**Source:** `p-2403` — <https://arxiv.org/abs/2403.12173>  
**TL;DR:** An LLM-driven, two-phase framework that auto-generates a coherent label taxonomy from a corpus (via summary-then-iterative-taxonomy-refinement) and then uses LLM pseudo-labels to train cheap classifiers for scale.

**Problem addressed.** How to turn a large corpus of unstructured text into a structured, meaningful set of category labels/tags with minimal human curation — solving both the "what should the label space even be?" problem (taxonomy induction) and the "how do we apply it at scale cheaply?" problem (classification). This is the same core problem the user faces: deriving a controlled, non-redundant tag vocabulary from arbitrary scraped content rather than letting tags proliferate ad hoc.

**Core method.** Phase 1 (taxonomy generation): each document is first compressed by an LLM into a short summary, so downstream reasoning operates over condensed representations instead of raw text. The taxonomy is then induced by an iterative, minibatch process explicitly framed as analogous to stochastic gradient descent: a current taxonomy "state" is carried forward, and for each minibatch of summaries the LLM runs a Generate-Update-Review loop — generate candidate labels, update/merge them into the running taxonomy, and review for quality, redundancy, and a target label cardinality. Over passes this converges to a compact, de-duplicated, mutually-distinct label set with names plus descriptions. Phase 2 (scaled classification): the LLM acts as a pseudo-labeler to assign these taxonomy labels to a large sample, and those pseudo-labels train lightweight supervised classifiers (e.g., logistic regression / shallow models) that are cheap to run over the full corpus. Evaluated on Bing Copilot conversation logs for user-intent and domain taxonomies, showing a good accuracy/cost tradeoff versus pure-LLM or pure-clustering baselines.

**Techniques.**
- LLM summarization as a dimensionality-reduction step before labeling
- Iterative minibatch taxonomy induction framed as LLM-as-optimizer / 'prompt-based SGD' over a taxonomy state
- Generate-Update-Review prompt loop per minibatch
- Explicit label-cardinality control to cap taxonomy size
- LLM-driven merging/normalization of duplicate and overlapping labels with distinctness enforcement
- Labels carry names + natural-language descriptions (not bare strings)
- LLM pseudo-labeling to bootstrap lightweight supervised classifiers for cheap scale-out
- Deterministic/interpretable evaluation of taxonomy quality (coverage, accuracy, distinctness)

**Relevance to this project.** Strongly validates several core design choices and improves on one. (1) Summarize-first: TnT-LLM confirms the user's plan to have an LLM summarize each object and derive tags from the summary — they show summaries are the right unit for label/tag extraction because they normalize length and noise. (2) Tag/concept-based over raw entities: the paper builds an abstract LABEL taxonomy (intents, domains, concepts) rather than surface entities, validating the user's tag-centric graph over a purely entity-extraction graph — tags generalize and connect documents that share no literal entities. (3) Tag-drift / normalization: this is the paper's biggest contribution to the project. The user's plan (a hash table that normalizes near-duplicate tags) is a purely string/lexical fix; TnT-LLM shows that drift is better controlled by maintaining a GLOBAL taxonomy STATE that an LLM incrementally merges new candidate tags into via the Generate-Update-Review loop with cardinality control. The user should treat their tag vocabulary as a living taxonomy updated in minibatches, not just a dedup hash — exact-hash normalization will miss semantic near-duplicates ('automobile' vs 'cars' vs 'vehicles') that this loop catches, and it lets you store a description per tag. (4) Embeddings: the paper does NOT embed on tags — it relies on LLM reasoning over summaries and trained classifiers. This is a mild challenge to the user's 'embed on tags' idea; tags are short and embedding them loses context, so embedding summaries (or tag+description) is likely better for retrieval recall, with the normalized tag set serving as the controlled graph-traversal vocabulary. (5) Scale path: Phase 2's pseudo-label-then-train-a-cheap-classifier pattern is a concrete way to tag the next 10k+ nodes without an LLM call per node once the taxonomy stabilizes on the ~100-article pilot.

**Pitfalls / limitations.**
- Text-only: the paper has no multimodal handling, so it gives no guidance on tagging the user's images — image summaries/tags would need a separate VLM step the paper does not cover
- Taxonomy induction is corpus-dependent and order/minibatch-sensitive; a taxonomy fit on 100 random Wikipedia articles may be unstable or skewed and need re-running as the corpus grows
- LLM-driven merge/review is non-deterministic and can over-merge (collapsing distinct concepts) or under-merge — needs evaluation guardrails
- It produces a relatively flat/controlled label set with bounded cardinality, which is great for tags but is NOT a graph or traversal method — it says nothing about bidirectional edges, link structure, or LLM traversal/'seen' flags
- Phase 2 classifiers assume a fairly stable taxonomy; frequent vocabulary churn forces retraining
- Cost of Phase 1 is front-loaded (one LLM summary + multiple taxonomy-update passes per minibatch)

**Key takeaways.**
- Summarize each object first, then extract tags from the summary — do not tag raw text/links directly; the summary is the normalization layer.
- Replace (or back) the tag-dedup hash table with a maintained global tag TAXONOMY updated via an LLM Generate-Update-Review loop with a target cardinality — this kills semantic tag drift that exact-hash normalization misses.
- Store a short description with each canonical tag; descriptions are what let the LLM (and you) decide merges and disambiguate during traversal.
- Prefer embedding summaries (or tag+description text), not bare tags, for search recall; use the normalized tag set as the controlled vocabulary for graph traversal rather than as the embedding target.
- After the tag taxonomy stabilizes on the ~100-article pilot, adopt the Phase-2 trick: use LLM pseudo-labels to train a cheap classifier so new nodes get tagged without a per-node LLM call.
- You still need a separate component for graph structure (bidirectional edges, traversal, the 'seen' flag) and for image tagging — TnT-LLM only solves the tag-vocabulary and tagging problem, not the graph or multimodal parts.

## Chain-of-Layer: Iteratively Prompting Large Language Models for Taxonomy Induction from Limited Examples (CIKM 2024)

**Source:** `cikm-3679608` — <https://dl.acm.org/doi/10.1145/3627673.3679608>  
**TL;DR:** An in-context-learning framework that builds a hierarchical taxonomy from a flat set of entities top-down, layer by layer, using an MLM-based ensemble ranking filter to prune hallucinated parent-child edges at each step.

**Problem addressed.** Taxonomy induction: given a flat pool of entities (words/short phrases) plus a root, organize them into a hypernym-hyponym (is-a) hierarchy. Naively asking an LLM to emit a whole taxonomy in one shot produces structural violations (multiple roots, cycles) and hallucinated entities/edges. The paper targets reliable hierarchy construction from limited few-shot examples while controlling hallucination.

**Core method.** Chain-of-Layer (CoL) decomposes taxonomy construction into per-layer iterations k=0,1,2,...: starting from the root, at each layer the LLM is prompted with the current partial taxonomy plus the full entity pool and asked to select which remaining entities belong at this depth and attach them as children of layer k-1 nodes. Taxonomy state is serialized in a Hierarchical Format (numbered outline like "1. science / 1.1 physics") so sibling and ancestor relationships are explicit in the prompt, preventing multi-root/cycle errors. After each layer, an Ensemble-based Ranking Filter validates every proposed child-parent edge: it plugs the pair into six "X is a kind of Y" templates, uses a masked LM (SciBERT) to score the parent token, ranks candidate parents, takes reciprocal-rank scores averaged across templates, keeps only top candidates and recycles rejected entities to later layers. This filter runs at every layer so errors are corrected before they propagate downward. The method needs only ~5 few-shot demonstrations (from WordNet) showing the layered decomposition.

**Techniques.**
- Top-down layer-by-layer iterative taxonomy construction
- Hierarchical Format (numbered-outline) serialization of graph state in the prompt
- Few-shot in-context learning (~5 WordNet demos)
- Ensemble-based Ranking Filter using a masked LM (SciBERT)
- Template-based hypernym scoring ('X is a kind of Y', 6 templates) with reciprocal-rank aggregation
- Per-layer hallucination filtering with entity recycling to later layers
- Constraint/rule prompting (single root, closed entity set, output format)

**Relevance to this project.** Strongly relevant and partly validating, partly cautionary for the tagged-graph plan. (1) Validates LLM-driven structure-building over a closed entity/tag set: CoL's pattern of giving the LLM the current partial graph plus the candidate pool and asking it to place nodes is exactly the kind of LLM-traversable construction the project wants, and the Hierarchical Format trick (serialize current graph state compactly in the prompt) is directly reusable when the LLM walks/extends the bidirectional graph. (2) Challenges pure tag-based design: CoL works on *typed* is-a edges between deduped entities, not free tags. It shows that to get a navigable hierarchy you need normalized, canonical entity names and explicit relation semantics, reinforcing the project's hash-table tag normalization but suggesting tags alone (untyped co-occurrence) won't yield clean traversal; consider promoting some tags to typed entities with is-a/related edges. (3) The Ensemble-based Ranking Filter is a concrete, cheap mechanism to fight "tag/edge drift" and hallucinated links: a small MLM (or an embedding-similarity gate) scoring candidate edges before commit maps directly onto the project's need to prevent near-duplicate/spurious tags and edges; it is an alternative/complement to the embedding hash table. (4) On embeddings: CoL relies on template+MLM scoring rather than tag/summary embeddings for relation validation, hinting that embedding-on-tags alone may be too coarse for relationship quality; embedding summaries or using a verification LM for edge confidence is worth adding. (5) Multimodal: CoL is text/entity-only — it offers nothing for the project's image-ingestion path; that part needs other sources. (6) Wikipedia relevance: CoL was evaluated on a Wikipedia-derived taxonomy (252 concepts, depth 3) and performed better on general-domain Wikipedia than specialized domains, which is encouraging for the project's ~100 random Wikipedia article test set.

**Pitfalls / limitations.**
- Scalability cliff: quality degrades sharply beyond ~80 entities per taxonomy; large graphs had to be sampled into 80-120 entity sub-taxonomies, so it does not directly scale to a large monolithic graph.
- LLMs fail to strictly obey instruction rules (single root, closed entity set) as scale grows, producing hallucinated or dropped entities.
- Only models layer-to-layer (parent-child) relations; ignores intra-layer / sibling and cross-cutting relationships — a real limitation for a richly cross-linked bidirectional graph.
- Assumes pre-extracted, clean single-word/short-phrase entities as input; it does not solve entity/tag extraction or dedup itself (the project still owns that).
- Tree/DAG-oriented (single root, is-a), not a general associative tagged graph; adapting it to many relation types or multi-parent tags needs extra work.
- Text-only; no multimodal/image handling.
- Filter depends on an MLM (SciBERT) tuned to general/scientific 'is-a' phrasing; template scoring may misjudge non-taxonomic 'related-to' edges the project cares about.

**Key takeaways.**
- Serialize the current graph state into the prompt in a compact, explicitly-structured format (numbered outline) so the LLM can extend/traverse it without producing cycles or orphan roots.
- Build/extend incrementally and validate each new edge before committing, rather than asking the LLM for the whole structure at once — this is the main hallucination-control lever.
- Add a cheap edge-verification gate (small MLM template scoring or embedding-similarity threshold) as a second line of defense against tag/edge drift, complementing the tag-normalization hash table.
- Distinguish typed entity relations (is-a) from free tags; canonicalizing entities and giving edges semantics yields far cleaner LLM traversal than untyped tag soup.
- Expect a per-prompt size ceiling (~80 nodes here): chunk the graph into bounded sub-views for any LLM construction/traversal step instead of feeding the whole graph.
- General-domain Wikipedia content is a favorable test bed for this style of LLM structuring, so the project's ~100-article benchmark is reasonable, but plan separately for images and for specialized/technical articles where quality drops.

## TaxoGen: Unsupervised Topic Taxonomy Construction by Adaptive Term Embedding and Clustering (KDD 2018)

**Source:** `kdd-3220064` — <https://dl.acm.org/doi/10.1145/3219819.3220064>  
**TL;DR:** Builds a topic taxonomy unsupervised by recursively spherical-clustering term embeddings top-down, where each node is a cluster of coherent terms and each subtree gets its own locally re-trained embeddings for sharper discrimination.

**Problem addressed.** Turning a flat corpus of terms/concepts into a navigable hierarchy (general topics at top, specific at bottom) without supervision or a predefined ontology. Directly relevant to organizing extracted tags/concepts into a traversable structure and to the "tag drift" problem, since it deals with grouping near-synonymous terms and separating general vs specific concepts.

**Core method.** TaxoGen represents each taxonomy node not as a single term but as a cluster of semantically coherent terms, and grows the tree top-down by recursion. At each node it runs adaptive spherical clustering (spherical k-means on L2-normalized term embeddings, i.e. cosine-similarity clustering on the unit sphere) to split a coarse topic into k child sub-topics. Two refinements fix the naive recursion: (1) a local embedding module that, for each sub-topic, retrieves a sub-corpus of only the documents relevant to that topic and re-trains SkipGram word embeddings on that narrow corpus, so that fine-grained distinctions invisible in the global embedding space become separable at lower levels; (2) an adaptive step that scores each term's representativeness for its assigned child cluster and, if a term is too "general" (high similarity to the parent / not concentrated in any one child), pushes it back up to the parent level rather than forcing it into a child. Representativeness combines popularity (term frequency within the cluster's sub-corpus) and concentration (relevance to its own cluster relative to sibling clusters), so generic terms float up and distinctive terms sink down. Recursion stops at a depth/size threshold.

**Techniques.**
- Top-down recursive taxonomy construction (each node = cluster of terms, not a single term)
- Spherical k-means clustering on L2-normalized embeddings (cosine similarity)
- Adaptive spherical clustering: push over-general terms up to the parent based on a representativeness threshold
- Term representativeness scoring = popularity (in-cluster TF) x concentration (vs sibling clusters)
- Local embedding: retrieve a topic-specific sub-corpus and re-train SkipGram embeddings per subtree for level-appropriate discrimination
- Sub-corpus retrieval via term/document relevance to the current topic

**Relevance to this project.** Strongly relevant and partly corrective to the design. (1) Tag-based vs entity-based: TaxoGen validates organizing knowledge around extracted terms/concepts (your tags) rather than raw entities — it treats a coherent term cluster as the unit of meaning, which is exactly a normalized tag group. Its representativeness = popularity x concentration is a ready-made, training-free heuristic the project could borrow to rank which tags are canonical for a node and to detect generic vs specific tags. (2) Embedding on tags vs summaries vs chunks: TaxoGen's central finding challenges a naive "embed all tags once globally" approach. A single global embedding space loses discriminative power for fine distinctions; their local-embedding insight argues that within a dense neighborhood of similar tags you may need a narrower, context-restricted comparison to separate near-duplicates. For the user's hash-table tag normalization this is a caution: global cosine similarity alone will both over-merge (collapse distinct-but-related tags) and under-merge depending on scale. Consider similarity computed within a candidate neighborhood, not one global threshold. (3) Dedup / tag-drift: the concentration criterion is a principled signal for normalization — a tag that appears diffusely everywhere is a generic/noise tag (push up / down-weight), while a concentrated tag is a real distinguishing concept; this is more robust than pure string/embedding nearest-neighbor merging. (4) Traversal strategy: TaxoGen produces an explicit general-to-specific hierarchy, which is far more LLM-traversable than a flat bidirectional tag graph — it suggests layering a coarse-to-fine topic hierarchy on top of the user's graph so an LLM can descend from broad to narrow instead of doing unguided neighbor-hopping with a "seen" flag. The "seen" flag + bulk-clear is an orthogonal traversal-bookkeeping mechanism TaxoGen does not address. (5) Multimodal: TaxoGen is text-only (term embeddings from word co-occurrence) — it offers nothing for the images in the Wikipedia test set; the user's plan to summarize images into text first and then tag is the right bridge, but this paper does not validate the image path.

**Pitfalls / limitations.**
- Text/term-only: relies on word co-occurrence embeddings (SkipGram); no multimodal/image handling, so the project's image-to-text-summary step is unaddressed by this work
- Local embedding re-trains SkipGram per subtree on a retrieved sub-corpus — computationally heavy and needs a sizable corpus per topic; on only ~100 Wikipedia articles the sub-corpora may be too small to retrain meaningful embeddings
- Pre-LLM era (2018): uses static word2vec-style embeddings, not contextual/LLM embeddings; an LLM-summary embedding approach may already capture much of what local embedding was hacking around
- Branching factor k (children per node) and stopping depth are hyperparameters, not learned — requires tuning
- Output is a strict tree, not a bidirectional graph; cross-links between sibling subtrees (which the user's bidirectional design wants) are not modeled
- Requires a candidate term/phrase set up front (mined from the corpus); quality depends heavily on that extraction, analogous to your tag-extraction quality

**Key takeaways.**
- Make tags the unit, score them: adopt popularity x concentration to rank canonical tags per node and to flag generic (push-up) vs specific (push-down) tags — a cheap, unsupervised normalization signal beyond string/embedding match.
- Don't trust one global similarity threshold for tag dedup: discrimination needed varies by scale/neighborhood, so compute merge decisions within local candidate neighborhoods to avoid both over- and under-merging tag drift.
- Layer a coarse-to-fine hierarchy over the bidirectional tag graph: a general-to-specific topic tree gives the LLM a principled descent path, far more traversable than unguided neighbor-hopping with a seen flag.
- Concentration is a built-in noise filter: tags that appear diffusely across many nodes are low-value/generic and should be down-weighted or hoisted, not used as primary edges.
- With modern LLM/contextual embeddings of summaries, you likely get TaxoGen's 'local discrimination' benefit for free — prefer summary-or-tag embeddings from an LLM over re-training static embeddings per subtree, especially given the small (~100 article) test corpus.

## TaxoCom: Topic Taxonomy Completion with Hierarchical Discovery of Novel Topic Clusters (WWW 2022)

**Source:** `www-3512002` — <https://dl.acm.org/doi/10.1145/3485447.3512002>  
**TL;DR:** A weakly-supervised framework that grows a partial topic taxonomy top-down by discriminatively re-embedding terms per node and clustering them into either known child topics or newly-discovered "novel" ones.

**Problem addressed.** How to build a hierarchical topic taxonomy (tree of term-clusters over an unlabeled document corpus) when you only have a partial/incomplete starting hierarchy as weak supervision. Fully unsupervised taxonomy construction can't hit a desired structure, and supervised methods need labeled docs; TaxoCom completes a seed taxonomy by inserting missing topics at both existing nodes and brand-new nodes, while keeping each node's term cluster coherent and the corpus well covered. This is essentially the "tag/category drift and incompleteness" problem: given some known categories, decide whether a new term/document belongs to an existing category or warrants a new one.

**Core method.** TaxoCom recursively expands the taxonomy in a top-down pass starting at the root. At each node c it runs two tightly-coupled steps. (1) Locally discriminative embedding: instead of one global embedding, it re-trains a spherical (von Mises-Fisher / cosine) text embedding using only the local sub-corpus relevant to node c, with a max-margin objective that makes terms discriminative among the known sibling sub-topics — supervision comes from "keyword sets" built by collecting all center terms in each child's subtree from the given partial hierarchy. (2) Novelty adaptive clustering: each child sub-topic is modeled as a vMF distribution; a term's novelty score is 1 minus its max softmax membership over known sub-topics, and a threshold tau_nov = (1 - 1/K_c)^beta splits terms into known-topic terms (assigned to nearest known sub-topic by cosine to the center term) versus novel-topic terms (clustered by spherical K-means into new sub-topics). It then mines "anchor terms" per cluster via a significance score combining semantic relevance (cosine to cluster center) and representativeness (integrity + BM25 distinctiveness + popularity in the sub-corpus), filters out generic terms, and picks the number of novel clusters K* by minimizing the standard deviation of vMF concentrations so novel topics have comparable specificity to known ones. Documents are assigned to the sub-topic maximizing a tf-idf weighted sum over assigned terms, producing the sub-corpus for the next recursion level.

**Techniques.**
- Top-down recursive taxonomy expansion (per-node processing)
- Spherical/von Mises-Fisher (vMF) text embedding with cosine similarity instead of Euclidean
- Locally discriminative embedding: re-train embeddings on the node's local sub-corpus only
- Keyword-guided max-margin discriminative loss using subtree center-terms as weak supervision
- Novelty score = 1 - max softmax membership over known sub-topic vMF distributions
- Adaptive novelty threshold tau_nov = (1-1/K_c)^beta to split known vs novel terms
- Spherical K-means clustering of novel-topic terms
- Anchor-term selection via significance = relevance x representativeness (integrity, BM25 distinctiveness, popularity)
- Automatic selection of number of novel clusters by minimizing std-dev of vMF concentration parameters
- tf-idf-weighted document-to-subtopic assignment

**Relevance to this project.** Directly relevant to the tag-normalization and "tag drift" core of the project, and it both validates and challenges several design choices. (1) Validates tag/concept-based graph over pure entity graph: TaxoCom explicitly contrasts itself with CoRel (entity is-a relation mining) and argues cluster-level concept/topic discovery generalizes better than entity-pair relations — supporting building the graph around tags/concepts rather than raw named entities. (2) Challenges flat hash-table dedup: the user's plan normalizes tags via a hash table (exact/near-duplicate string match). TaxoCom shows the harder problem is semantic, context-dependent normalization — the SAME term can be generic at one node and discriminative at another, and whether a tag is a duplicate vs a genuinely new category depends on local context, not a global string table. The novelty score + adaptive threshold is a principled, embedding-based alternative/supplement to the hash table: before minting a new tag, compute its membership softmax against existing sibling tags and only create a new tag if novelty exceeds threshold. This is a much better defense against tag drift than string hashing alone. (3) Embedding on tags vs summaries vs chunks: TaxoCom embeds TERMS (the unit closest to the user's "tags"), strongly supporting the user's instinct to embed tags. But its key finding is that a single global tag-embedding is NOT discriminative for fine-grained distinctions; embeddings should be re-fit locally per neighborhood. For an LLM-traversable graph this suggests either local re-embedding per subgraph or storing both a global embedding (for broad search) and tag-summary context for local disambiguation. (4) Traversal strategy: the top-down recursive node-by-node expansion is a natural template for the LLM's traversal and for the per-node "seen" debug flag — process a node, decide which existing neighbors a new item belongs to vs whether it needs a new node, recurse. (5) Hierarchy vs bidirectional graph: TaxoCom produces a strict tree; the user wants a bidirectional general graph. The known-vs-novel assignment logic transfers, but the user gets more flexibility (a tag can link to multiple parents) which TaxoCom's tree cannot represent. (6) Multimodal: TaxoCom is text-only (NYT + arXiv abstracts), so it offers nothing for the image side — the user's LLM-summarize-then-tag pipeline (turning images into text summaries before tagging) is the right bridge and is outside TaxoCom's scope.

**Pitfalls / limitations.**
- Text-only: evaluated on NYT articles and arXiv abstracts with no image/multimodal handling, so nothing transfers to the user's photo ingestion except via prior text summarization.
- Produces a strict tree, not a bidirectional/multi-parent graph; the assignment math assumes each term/doc belongs to exactly one sub-topic ('most relevant sub-topic'), which conflicts with overlapping tags.
- Requires a meaningful partial seed hierarchy as weak supervision; on a cold start with no known categories there is nothing to be discriminative against (the local discriminative embedding degenerates at the root).
- Per-node re-embedding is expensive: a fresh local spherical embedding is trained at every node of the tree, which scales poorly versus a single global embedding over ~100 articles but balloons on larger corpora.
- Several sensitive hyperparameters: novelty threshold exponent beta, margin m, vMF concentration kappa, number of novel clusters K* (they note DBSCAN was too hyperparameter-sensitive to use).
- Center-term / topic-name quality drives everything: weak supervision is just the surface name of each topic, so noisy or ambiguous tag names propagate errors down the recursion.
- Pre-LLM-era method (classical phrase mining via AutoPhrase/SegPhrase + SkipGram-style spherical embeddings); an LLM can now do summary-to-tag extraction directly, so TaxoCom's value to the project is the novelty/dedup decision logic, not its embedding pipeline.

**Key takeaways.**
- Replace pure string-hash tag dedup with a semantic novelty check: compute a new tag's softmax membership against existing sibling tags and only mint a new tag/node when novelty exceeds an adaptive threshold — this directly attacks 'tag drift' better than exact-match normalization.
- Tag normalization is context-dependent: the same tag can be generic in one region of the graph and discriminative in another, so dedup decisions should be made locally relative to a node's neighbors, not globally.
- Embedding tags (terms) is sound, but one global embedding loses fine-grained discrimination; consider local/contextual re-embedding or pairing global tag embeddings with local context for disambiguation during traversal.
- Use cosine/spherical similarity (vMF) rather than Euclidean for tag/term similarity and search — it aligns training with usage and cleanly supports softmax-style membership scoring.
- Score candidate tags by relevance x representativeness (is it coherent, distinctive vs siblings, and frequent in the relevant subset) to filter generic, low-information tags before they pollute the graph.
- Top-down recursive node processing maps cleanly onto an LLM traversal loop with a per-node 'seen' flag: visit node, assign new items to existing neighbor tags or spawn a new tag, recurse.

## From Louvain to Leiden: guaranteeing well-connected communities

**Source:** `p-1810` — <https://arxiv.org/abs/1810.08473>  
**TL;DR:** A faster, higher-quality community-detection algorithm that fixes Louvain's tendency to produce badly-connected (even internally disconnected) communities — the standard clustering primitive used to build hierarchical "community summaries" in graph-RAG systems.

**Problem addressed.** Community detection partitions a graph into densely-connected clusters by greedily optimizing a quality function (modularity or CPM). The dominant method, Louvain (2008), has a subtle but serious defect: as it moves nodes between communities, a node that acted as the sole bridge holding a community together can be moved away, leaving the community internally disconnected — yet Louvain never re-checks connectivity. The authors empirically show up to 25% of communities are badly connected and up to 16% are entirely disconnected, and that iterating Louvain makes this worse, not better. This is not a graph embedding or GNN paper; it is a graph-partitioning / clustering algorithm. For a graph database that wants to group related nodes into coherent topical clusters (e.g., for hierarchical navigation or summary nodes), the quality and connectivity of those clusters matters directly.

**Core method.** Leiden runs three repeated phases. (1) Local moving: like Louvain, move individual nodes to the neighboring community that most increases the quality function — but using a "fast local move" that maintains a queue/frontier of only the nodes whose neighborhoods changed, instead of re-scanning all nodes every pass, which is the main speedup. (2) Refinement: within each community found in phase 1, re-partition it into sub-communities, allowing a community to be split; crucially, nodes are only merged into a sub-community if doing so keeps it well-connected, and merges are made stochastically among quality-improving options rather than strictly greedily. This refinement is what guarantees every final community is internally connected. (3) Aggregation: build a smaller graph whose nodes are the refined sub-communities (but initialized using the phase-1 partition as the starting assignment), then recurse. Iterating the whole procedure provably converges to a partition where all subsets are locally optimally assigned. It supports both modularity and the Constant Potts Model (CPM, which avoids modularity's resolution limit). It is faster than Louvain and produces strictly better partitions with connectivity guarantees.

**Techniques.**
- Leiden community detection (three-phase: local move, refinement, aggregation)
- Fast local move with a node queue/frontier (only revisit nodes whose neighbors moved)
- Refinement phase that splits communities and enforces internal connectivity
- Randomized/stochastic merging among quality-improving moves (escapes greedy local optima)
- Modularity optimization
- Constant Potts Model (CPM) quality function to avoid the modularity resolution limit
- Hierarchical aggregation enabling multi-resolution / multi-level clustering

**Relevance to this project.** Directly relevant if the project ever wants topical structure over its bidirectional tagged graph rather than pure point-to-point traversal. Leiden is the exact algorithm Microsoft GraphRAG uses to cluster an entity/tag graph into nested communities and then LLM-summarize each community — which is almost identical to this project's "LLM summarizes each object" idea, but applied one level up at the cluster level. Validates and improves several design choices: (1) Tag-based vs entity-based graph: Leiden clusters by edge structure regardless of node type, so a tag-centric graph works fine as input — but cluster quality depends on edges being meaningful. If tags are only attributes (not nodes) the project should project a tag-cooccurrence or node-similarity graph before clustering. (2) Traversal strategy: this offers an alternative/complement to LLM-walks-the-graph — precompute communities offline, attach a community-summary node, and let the LLM first pick a community then descend, giving cheap coarse-to-fine navigation over ~100 Wikipedia articles instead of unguided hops. (3) Dedup/tag-normalization: orthogonal — Leiden does not normalize tags; the hash-table dedup must run first, because tag drift creates spurious distinct nodes that fragment communities and degrade clustering. (4) Embedding on tags vs summaries: orthogonal — Leiden uses graph topology, not embeddings, and is a useful non-embedding retrieval backbone that complements tag-embedding search. (5) Multimodal: irrelevant at the algorithm level; images only matter via whatever tags/edges the LLM extracts from them. The "seen" debug flag and bulk-clear are unaffected. Note CPM over modularity if the project cares about controllable cluster granularity.

**Pitfalls / limitations.**
- Not an embedding, GNN, or retrieval method — it only partitions an existing graph; it produces no vectors and does no semantic matching on its own.
- Requires a meaningful edge structure. A graph where tags are mere attributes (not connected nodes) gives Leiden nothing to cluster; you must first build node-node or tag-cooccurrence edges.
- Modularity has a resolution limit (merges small real communities at large scale); use CPM and tune the resolution parameter, which adds a hyperparameter to manage.
- Results are stochastic (depends on random seed and node order) and clusters are not stable across runs — bad if you need deterministic, reproducible cluster IDs without pinning a seed.
- At ~100 nodes the connectivity defect Leiden fixes is minor; the payoff (and the speed advantage over Louvain) only becomes significant on large graphs (10k-millions of nodes).
- Community detection is a separate offline batch step; it does not update incrementally as new objects are ingested, so you must re-cluster (or accept staleness) as the graph grows.

**Key takeaways.**
- If you want hierarchical/topical navigation, adopt Leiden (not Louvain) as the clustering primitive — it is the de-facto standard in graph-RAG (GraphRAG) for exactly this, and gives connected, higher-quality clusters faster.
- Run tag normalization/dedup BEFORE any clustering: near-duplicate tags fragment communities and silently degrade cluster quality.
- Treat communities as a complement to LLM traversal, not a replacement: precompute community summaries so the LLM navigates coarse-to-fine (pick community, then descend) instead of doing expensive unguided hops.
- Prefer CPM with a tunable resolution parameter over plain modularity if you need control over how coarse or fine the clusters are, and to dodge modularity's resolution limit.
- Make sure your tag graph actually has node-to-node edges with real semantics; clustering is only as good as the edge structure, so design edges (cooccurrence, shared-tag, embedding-kNN) deliberately, and remember the technique is graph-topology-based, orthogonal to your tag/summary embeddings.
