# Briefing: Production KG-Memory Frameworks vs. the Locked Architecture

## 1. What each system is (and how they differ)

**cognee** is a data-engineering framework for agent memory: an Extract-Cognify-Load pipeline that turns heterogeneous sources into three parallel storage planes (relational metadata + vector + typed graph). Its defining bet is the **DataPoint ontology** — typed Pydantic classes whose field type-hints auto-materialize as both graph edges and embedding targets — plus optional RDF/OWL ontology validation with a per-node `ontology_valid` trust flag. Retrieval is multi-mode (`SearchType` enum with auto-routing), flagship being GRAPH_COMPLETION: vector-seed → BFS graph-walk → LLM-compose. It is the heaviest and most schema-rigid of the three.

**mem0** is a lightweight memory layer whose signature is **write-time LLM reconciliation**: every new fact is embedded, compared against its top-k nearest existing memories, and an LLM emits a structured ADD/UPDATE/DELETE/NOOP tool call so the store stays deduplicated and contradiction-free on ingest. Its graph variant (mem0g) builds free-form (src, relation, dst) triplets and soft-invalidates contradicted edges. Crucially, the v3 OSS rewrite (Apr 2026) *abandoned* both the per-write reconciliation and the external graph, collapsing to single-pass ADD-only with an entity-overlap retrieval boost — a cautionary signal about graph ROI at scale. It differs from the other two by mutating state synchronously at write time rather than appending.

**graphiti** is a temporally-aware real-time graph for agent memory. It ingests immutable **Episodes**, LLM-extracts entity/edge triplets (with a reflexion self-critique pass), and is defined by its **bi-temporal edge model**: every fact carries validity windows (t_valid/t_invalid) and transaction times, and contradictions *invalidate* rather than delete prior edges, preserving full history. Retrieval uses **no LLM at query time** — parallel cosine + BM25 + n-hop BFS, fused by pluggable rerankers (RRF/MMR/node-distance/cross-encoder). It assumes a server graph DB (Neo4j/FalkorDB); no NetworkX/SQLite path. It differs by treating time and provenance as first-class, where cognee treats schema/ontology as first-class and mem0 treats write-time consolidation as first-class.

## 2. Where they AGREE with the locked architecture

- **Local prototype stack is legitimate.** cognee's recommended fully-local stack is SQLite + Kuzu/NetworkX + local sentence-transformers — nearly identical to the project's NetworkX + SQLite + local sentence-transformers. (Kuzu is the noted upgrade path past ~10k nodes.)
- **Summary-first pipeline.** cognee summarizes during cognify and extracts entities from chunks; this validates the project's "summarize → extract tags/entities from the summary" ordering.
- **Embed summaries as primary, entity/tag strings secondarily.** Matches cognee's per-field embedding metadata, mem0's "facts primary, entity strings secondary," and graphiti's split of edge-fact vs. entity-name embeddings. All three confirm this exact split.
- **Append + batch reconcile over online mutation.** cognee deliberately makes graph rebuild *explicit* ("you decide when the graph reconciles") rather than mem0's per-write mutation — and mem0 v3 itself retreated from per-write reconciliation. Two independent data points validate the project's batch-reconcile bet.
- **Layered, cheap-first dedup.** Both cognee (exact/hash → difflib fuzzy 0.80 / MinHash-LSH → LLM/ontology fallback) and graphiti (cosine + BM25 → entropy-gated fuzzy → LLM resolution) implement almost exactly the project's "hash → embedding synonymy → batch taxonomy reconcile" ladder. Strong validation of the core tag-drift design.
- **No-LLM-at-query-time retrieval is viable.** graphiti's entire retrieval path avoids query-time generation; this validates the project's PPR seed-and-spread as a defensible low-latency choice.
- **Free-form LLM tags are a workable choice.** mem0g uses free-form LLM entity/relation labels with no ontology, confirming the project doesn't *need* cognee's ontology to function.
- **GraphRAG-style community summaries.** graphiti builds community clusters with rolled-up map-reduce summaries — confirms the project's community-summary design.

## 3. Where they CHALLENGE it

**(a) mem0's write-time ADD/UPDATE/DELETE/NOOP vs. append-then-batch-reconcile.**
mem0's thesis is the inverse of the project's: it keeps the store *always* consolidated by handing each new fact + its nearest neighbors to an LLM that decides the operation synchronously. The challenge isn't "switch to per-write" (mem0 itself abandoned this in v3 for cost/latency, and at 200 nodes it's overkill) — it's that the project's batch reconcile has **no LLM tie-breaker at all** for the ambiguous middle cases. Reconsider: keep the cheap hash + embedding layers, but borrow mem0's *structured* ADD/UPDATE/MERGE/NOOP tool-call as a selective final arbiter, invoked only when embedding synonymy is ambiguous. This is a targeted upgrade to the reconcile step, not a redesign.

**(b) graphiti's bi-temporal model + edge invalidation vs. the static graph.**
graphiti versions every fact with validity windows and invalidates (never deletes) superseded edges, preserving queryable history. The project's static append graph has **no invalidation path** — once a fact is in, a later contradicting ingest cannot supersede it without a destructive mutation. For a 100-Wikipedia-article snapshot corpus this is largely fine (Wikipedia facts are stable; you ingest snapshots, not an event stream), so full bi-temporality is unjustified. But the cheap version is worth adopting: a per-edge/per-node `valid` / `superseded_by` flag (a real-data sibling of the existing `seen` debug flag) so re-ingestion can soft-invalidate rather than mutate or duplicate. Skip the LLM date-parsing quad — that's where graphiti silently corrupts its time model.

**(c) cognee's ontology/typed-DataPoints vs. free-form LLM tags.**
cognee's headline differentiator is ontology-grounded canonicalization to canonical URIs with an `ontology_valid` trust flag — turning unbounded tag drift into a *bounded* canonicalization problem. The project's free-form tags + drift control is a lighter reinvention of the same problem. Two specific things to reconsider, short of adopting a full OWL ontology (which is real maintenance work and the project may not want it): (1) **constrain the relation vocabulary** — both cognee and graphiti show free-form relations collapse to vague MENTIONS/RELATES_TO edges; a small fixed relation enum makes the graph richer; (2) **add a per-node/edge `confidence` / `valid` flag** for trust-based retrieval filtering — cheap, and pairs naturally with the `seen` flag. Note the counter-evidence: cognee's `difflib` fuzzy at 0.80 is *weaker* than the project's embedding-synonymy layer for semantically-distinct-but-lexically-similar tags — do **not** trade embedding synonymy for string fuzz.

**(d) Their retrieval stacks (hybrid semantic+BM25+graph + reranking) vs. PPR-only.**
None of the three use Personalized PageRank. cognee = vector-seed + BFS + rerank; mem0 = vector top-k (+ entity boost); graphiti = parallel cosine + BM25 + n-hop BFS fused by RRF/MMR/node-distance/cross-encoder rerankers. The shared lesson: **PPR should be one mode among several, not the only path, and it should not be the seed signal.** Reconsider: (1) add BM25/keyword as a parallel seed signal alongside embeddings before PPR spread (graphiti, mem0 v3 both fuse lexical + semantic); (2) layer **MMR (diversity) and node-distance (query-anchored) reranking on top of PPR scores** (graphiti); (3) expose multiple retrieval modes with auto-routing so PPR-spread can be A/B'd against plain BFS (cognee) — important because PPR may be overkill at 200 nodes and you need to *prove* it beats BFS at that scale.

## 5. What to explicitly NOT adopt

- **cognee's full RDF/OWL ontology layer.** Without a supplied ontology everything is marked unvalidated and you're back to free-form anyway; building/maintaining an ontology is real work unjustified at prototype scale. Take the *confidence flag* and *constrained relations*, not the ontology engine. (cognee)
- **cognee's DataPoint "type-hints become edges" magic.** Convenient but couples schema tightly to graph structure — refactoring a Pydantic field silently changes the graph. The project's free-form tags avoid this rigidity. (cognee)
- **mem0's per-write LLM reconciliation as the default path.** Expensive, latency-heavy, and mem0 *itself* removed it in v3. Use the cheap layers first; reserve the LLM only for ambiguous tie-breaks. (mem0)
- **Hard-delete on LLM-judged contradiction.** Can erase correct facts on a hallucinated conflict. Always soft-invalidate. (mem0g)
- **graphiti's full bi-temporal quad with LLM date-parsing.** Mis-parsed valid_at/invalid_at silently corrupts the time model; unjustified for a stable Wikipedia snapshot corpus. Take the soft-invalidation flag, not the quad. (graphiti)
- **A server graph DB (Neo4j/FalkorDB) and graphiti's storage code.** At 200 nodes NetworkX is fine and gives free PPR (graphiti has none). (graphiti)
- **The frameworks' dependency weight wholesale.** cognee's many backends + async task framework, mem0's vector-store abstraction layer — all overkill at 200 nodes. Borrow patterns, not dependencies. (cognee, mem0)
- **cognee's `difflib`-at-0.80 in place of embedding synonymy.** Brittle for semantically-distinct-but-lexically-similar tags; the project's embedding layer is stronger here. Keep it. (cognee)

## 6. Build-or-borrow call

**Recommendation: keep building your own on NetworkX. Borrow patterns from all three; vendor none.**

The decisive factors:

1. **Your stack is genuinely well-suited, not a compromise.** cognee independently arrived at the *same* local stack (SQLite + NetworkX/Kuzu + local sentence-transformers), confirming it's a legitimate prototype-scale choice rather than a beginner's shortcut. At 200 nodes, NetworkX also gives you **free Personalized PageRank** — which neither cognee nor graphiti nor mem0 implements. Your central novel/defensible bet (PPR seed-and-spread) is *only* easily available on your own stack. Vendoring graphiti would force a server graph DB and you'd lose PPR entirely; vendoring cognee would hand you BFS, not PPR.

2. **This is a learning build, and the frameworks' value is their patterns, not their code.** Every concrete thing worth taking (structured extraction, entropy-gated fuzzy, soft-invalidation, layered dedup, multi-mode retrieval, reranking) is a ~10-50 line pattern, not a subsystem. Adopting the dependencies would bury the learning under opinionated machinery (cognee's ECL task framework, mem0's abstraction layers) that is pure overkill at this scale.

3. **mem0 v3's retreat is the clinching signal.** A major framework looked at its own traversable external graph and *removed it* as not worth the cost, collapsing to an entity-overlap retrieval boost. That tells you a heavy graph subsystem is questionable ROI even in production — so importing one for a 200-node prototype is the wrong direction. Build the minimal graph you need and prove PPR earns its place against BFS.

**The tradeoff you accept:** you forgo battle-tested entity resolution and graphiti's correct bi-temporal model. Mitigation: the corpus is a stable Wikipedia snapshot (bi-temporality is genuinely unneeded — take only the soft-invalidation flag), and the adopt list above ports the high-value resolution patterns directly.

**One caveat to watch:** if the project ever grows past ~10k nodes or needs a real changing-fact event stream, revisit — Kuzu (cognee's embedded upgrade path, drop-in-ish from NetworkX) for scale, or graphiti for genuine temporal correctness. Below that threshold, build.

## Appendix — per-framework deep reads

### cognee (topoteretes/cognee)

**TL;DR:** "Memory for AI agents" framework that turns heterogeneous data into a typed knowledge graph + vector store via a modular Extract-Cognify-Load (ECL) pipeline, queried through a multi-mode SearchType API with GRAPH_COMPLETION (seed vectors -> walk graph -> LLM answer) as the flagship.  
**License:** Apache-2.0 (permissive; OSS core. cognee also offers a hosted/managed "cogwit" product, but the library is Apache-2.0).

- **Architecture:** cognee frames agent memory as a data-engineering problem: an ECL (Extract-Cognify-Load) pipeline composed of swappable Tasks. Extract = ingestion of raw sources (PDFs, text, Slack/Notion, images, audio) into a relational metadata store. Cognify = the core enrichment step: document classification, semantic chunking, LLM-driven entity/relationship extraction with summarization, ontology validation, and persistence across graph + vector + relational backends, plus foreign-key edge derivation. Load = writing vector embeddings and graph edges to the configured backends. Three storage planes run in parallel: a relational store (SQLite/Postgres) for metadata, a vector store for embeddings, and a graph store for the typed knowledge graph. Retrieval is a separate stage exposing many SearchType modes. The whole thing is meant to run locally on a light stack (SQLite + LanceDB + Kuzu/NetworkX) or scale out (Postgres + Qdrant/PGVector + Neo4j).
- **Graph model:** The graph is built from a DataPoint ontology: typed Pydantic classes whose field type hints automatically become graph edges at runtime. E.g. a DocumentChunk declares `is_part_of: Document` and `contains: List[Entity]`, and those annotations are materialized as edges between nodes. The same class also drives vector indexing via metadata declaring which fields get embedded — one definition serves both graph structure and embedding. LLM extraction emits a typed `KnowledgeGraph` Pydantic model (lists of Node and Edge objects). Entities are first-class nodes; node types are typed entities with canonical names and an `ontology_valid` flag. Edges carry relationship types and distinguish LLM-extracted vs. ontology-inherited (RDF subclass/object-property) relationships. Temporal handling is OPTIONAL: cognee has a "temporal mode" where old and new facts coexist as dated events, but the default graph is essentially static/append — there is no built-in bi-temporal edge invalidation like Graphiti.
- **Extraction:** LLM-driven structured extraction using Instructor to constrain output to a Pydantic `KnowledgeGraph` schema (Node/Edge lists) rather than free-form text. Extraction runs at the document-chunk level; the LLM names entities WITHOUT initial constraints, and canonical standardization happens later in the pipeline. Optionally guided by an ontology: an RDFLibOntologyResolver parses OWL/RDF/Turtle/N-Triples/JSON-LD into cached class/individual lookup dicts, and extracted entity types are mapped onto ontology classes. When no ontology is supplied it degrades gracefully (all entities marked unvalidated). Summarization is part of the cognify task chain.
- **Dedup / conflict:** Entity resolution happens during cognify, primarily via a FuzzyMatchingStrategy: exact match against normalized lookups first, then fuzzy fallback using Python difflib.get_close_matches() with a configurable threshold (default 0.80), then replacement of LLM-derived names with canonical ontology-derived URIs (e.g. "car manufacturer"/"automobile maker" -> CarManufacturer). Nodes get an `ontology_valid` flag for trust-based downstream filtering. Some sources describe a deterministic MinHash/LSH fast path with LLM fallback plus edge dedup and contradiction resolution. Crucially, dedup/reconciliation is tied to an explicit rebuild step — you decide WHEN the graph rebuilds, rather than mem0's per-write LLM ADD/UPDATE/DELETE. Conflicts are not auto-invalidated by default; temporal mode keeps contradictory facts as coexisting dated events.
- **Embeddings:** DataPoint metadata declares which fields are embedded, so embeddings are generated per indexable field during cognify and written to the vector store. Supports local (sentence-transformers / Ollama) and hosted embedding providers. Vector store backends: LanceDB (light/default-local), Qdrant, PGVector, Weaviate (and Redis integration exists). Embeddings cover chunk/summary text and entity strings, enabling both dense semantic recall and vector-seeded graph entry.
- **Retrieval:** Multiple retrieval modes via a large `SearchType` enum, with auto-routing to pick a strategy. Flagship is GRAPH_COMPLETION: seed via vector lookup, walk matching triples through the graph (breadth-first traversal / multi-hop), then hand the assembled subgraph to an LLM for answer composition. Other modes include RAG/dense-vector completion, INSIGHTS, CHUNKS, SUMMARIES, CODE, sparse/BM25, and hybrid. Retrieval combines cosine similarity + BM25 + breadth-first graph traversal with pluggable rerankers. So it is LLM-at-query-time for the completion modes. Note: cognee does NOT center Personalized-PageRank seed-and-spread the way the project plans — its traversal is BFS over vector-seeded nodes.
- **Storage backends:** Graph: NetworkX (local default for prototyping), Kuzu (embedded local, increasingly the local default), Neo4j, FalkorDB. Vector: LanceDB, Qdrant, PGVector, Weaviate (Redis integration available). Relational/metadata: SQLite (local) or Postgres. All three planes are pluggable; the recommended fully-local stack is SQLite + LanceDB + Kuzu (or NetworkX).
- **Relevance to project:** Strong structural overlap, which validates several project decisions. (1) Backend choice: cognee's recommended local stack is SQLite + Kuzu/NetworkX + local sentence-transformers — nearly identical to the project's NetworkX + SQLite + local sentence-transformers, confirming this is a legitimate prototype-scale combo (Kuzu is worth noting as an embedded upgrade path beyond NetworkX once >~10k nodes). (2) Summary-first pipeline: cognee also summarizes during cognify and extracts entities from chunks, validating the project's "LLM summarizes -> extract tags/entities from the summary" ordering. (3) Embedding both summaries and entity/tag strings matches cognee's per-field embedding metadata. (4) Append + batch reconcile vs. per-write mutation: cognee deliberately makes the rebuild EXPLICIT (decide when the graph reconciles) rather than mem0's per-write LLM ADD/UPDATE/DELETE — this directly validates the project's "append + batch taxonomy reconcile" over mem0's online mutation. WHERE IT CHALLENGES THE PROJECT: (a) Retrieval — cognee uses vector-seed + BFS graph-walk + rerank, NOT Personalized-PageRank seed-and-spread; PPR is more novel/defensible but the project should confirm it beats simple BFS at 200 nodes (PPR may be overkill at that scale). (b) Free-form tags vs. ontology — cognee's headline differentiator is ontology-grounded canonicalization with an ontology_valid trust flag; the project's free-form tags + tag-drift control is a lighter-weight reinvention of the same problem. cognee shows a layered answer (deterministic fuzzy/MinHash fast path -> LLM/ontology fallback) that maps almost exactly onto the project's "hash + embedding synonymy + batch taxonomy reconcile." (c) Static graph vs. temporal — like the project, cognee's default graph is static; if temporal correctness matters, Graphiti's bi-temporal edge invalidation is the alternative to weigh.

**Notable techniques:**
- DataPoint ontology: Pydantic field type-hints auto-materialize as graph edges AND drive vector indexing from one class definition
- Instructor-constrained LLM extraction into a typed KnowledgeGraph (Node/Edge) Pydantic schema
- Composable Task/Pipeline abstraction for ECL — custom tasks chained into pipelines
- Optional RDF/OWL ontology validation: RDFLibOntologyResolver + fuzzy class mapping + subgraph expansion injecting inherited subclass/object-property edges + per-node ontology_valid trust flag
- FuzzyMatchingStrategy (difflib, threshold 0.80) with exact-match fast path; MinHash/LSH deterministic path + LLM fallback for entity resolution
- Explicit, user-triggered rebuild rather than per-write memory mutation
- Multi-mode SearchType retrieval with auto-routing; GRAPH_COMPLETION = vector-seed -> graph-walk -> LLM-compose
- Optional temporal mode where contradictory facts coexist as dated events
- Foreign-key edge derivation from relational data

**What to adopt:**
- DataPoint pattern: define nodes as typed Pydantic classes where field type-hints both create edges and declare which fields get embedded — collapses the project's schema, graph-build, and embedding-selection into one source of truth.
- Use Instructor (or equivalent structured-output) to force Claude Haiku's extraction into a typed KnowledgeGraph(Node[], Edge[]) schema instead of parsing free text — directly improves extraction reliability.
- Layered entity resolution exactly mirrors the project's tag-drift plan: exact/hash fast path -> deterministic fuzzy or MinHash/LSH -> LLM/ontology fallback. Adopt the difflib threshold (~0.80) and MinHash/LSH as a cheap middle layer before spending embedding/LLM calls.
- Add an `ontology_valid` / confidence flag per node+edge so retrieval can do trust-based filtering — cheap to add, useful for debugging alongside the project's 'seen' flag.
- Multi-mode SearchType + auto-routing: expose distinct retrieval modes (graph-completion, pure-vector RAG, summaries, raw chunks) rather than one hardcoded path; lets you A/B PPR-spread vs. BFS.
- Explicit batch rebuild semantics (cognee's 'you decide when the graph rebuilds') validate doing taxonomy reconcile as a discrete batch job rather than online.
- Consider a lightweight optional ontology to anchor tags/entities to canonical URIs — turns free-form tag drift into a bounded canonicalization problem.

**Pitfalls:**
- cognee's marketing ('cognitive-science-grounded ontology', 'self-improving memory') massively overstates what is mechanically a chunk->LLM-extract->fuzzy-canonicalize->BFS-retrieve pipeline; don't be misled into thinking there's special graph reasoning.
- The DataPoint 'type-hints become edges' magic is convenient but couples schema tightly to graph structure — refactoring a Pydantic field can silently change the graph; the project's free-form tags avoid this rigidity at the cost of drift.
- Ontology validation only helps if you actually supply an OWL/RDF ontology; without one everything is marked unvalidated and you're back to free-form extraction — building/maintaining an ontology is real work the project may not want.
- Default graph is NOT temporal/bi-temporal; contradictions are not auto-resolved unless you opt into temporal mode where stale facts simply pile up as dated events — can bloat the graph. If the project needs fact-updating, neither cognee's default nor a static append model handles it; look at Graphiti.
- Retrieval is LLM-at-query-time for completion modes (extra latency + cost per query) — the project's PPR seed-and-spread could answer some queries without an LLM call; don't blindly copy GRAPH_COMPLETION.
- cognee is heavy/opinionated (many backends, pipeline framework, async tasks); at ~200 nodes most of its machinery is overkill — borrow patterns, don't adopt the dependency.
- Fuzzy difflib matching at 0.80 is brittle for semantically-distinct-but-lexically-similar tags; the project's embedding-synonymy layer is actually stronger here and should not be dropped in favor of pure string fuzz.

### mem0 (incl. mem0g graph memory)

**TL;DR:** A memory layer for LLM apps that uses an LLM at write-time to extract facts and run an explicit ADD/UPDATE/DELETE/NOOP reconciliation against retrieved similar memories, with an optional graph variant (mem0g) that stores entity-relationship triplets and marks contradicted edges invalid for temporal reasoning.  
**License:** Apache 2.0 (open-source SDK). A separate hosted/managed Mem0 Platform is commercial.

- **Architecture:** mem0 has two phases. Extraction: given a new message pair plus a rolling conversation summary and recent-message window, an LLM extraction function produces candidate "facts" (salient memories). Update/consolidation: for each candidate fact, the system embeds it, vector-searches the top-s most semantically similar existing memories, and hands the fact + those neighbors to an LLM that issues a tool call choosing ADD/UPDATE/DELETE/NOOP. The graph variant mem0g additionally runs an entity extractor and a relationship generator to build a directed labeled graph of (source, relation, destination) triplets in a graph DB. NOTE the version split: the arxiv paper (2504.19413, Apr 2025) and most docs describe this LLM-reconciliation + external-graph design; an open-source v3 rewrite (PR #4805, Apr 2026) replaced it with a single-pass ADD-only extractor and removed the external graph module in favor of an in-vector-store entity collection used only as a retrieval boost. Storage is an abstracted vector store + optional graph store; the hosted platform has a built-in always-on graph.
- **Graph model:** mem0g (classic): directed labeled graph G=(V,E,L). Nodes are entities, each with a semantic type label (Person, Location, Event, etc.), an embedding vector, and metadata. Edges are relationships expressed as triplets (v_source, relation, v_destination) with labels like lives_in, prefers, owns, happened_on. Entities and edges are first-class graph objects. Temporal/versioning: rather than physically deleting contradicted relationships, the update resolver marks them invalid/obsolete, preserving history for temporal reasoning (a soft-delete versioning model, not full bi-temporal timestamps like Graphiti). v3 OSS: no explicit graph schema at all — entities (proper nouns, quoted text, compound noun phrases) are extracted into a parallel {collection}_entities vector collection; "edges" are implicit (memories sharing an entity are linked) and exist only to boost retrieval scores.
- **Extraction:** LLM-based, two-stage in the graph variant. Plain mem0: one extraction prompt over (message pair + conversation summary + recent window) yields candidate facts. mem0g: EXTRACT_ENTITIES_TOOL identifies entities and assigns semantic type labels; a RELATIONS_TOOL / relationship generator then derives labeled triplets between those entities. Operations are emitted as structured tool calls (ADD_MEMORY_TOOL_GRAPH, UPDATE_MEMORY_TOOL_GRAPH, DELETE_MEMORY_TOOL_GRAPH, NOOP_TOOL) rather than free text. No fixed ontology is imposed — entity types and relation labels are LLM-generated on the fly (free-form, schema-light), unlike cognee's typed DataPoints/ontology.
- **Dedup / conflict:** This is mem0's signature mechanism. At write time, each new fact is compared (via top-s vector retrieval of similar existing memories) and the LLM decides: ADD (no semantically equivalent memory exists), UPDATE (augment/refine an existing memory with complementary or more-recent info), DELETE (new info contradicts an existing memory), or NOOP (already covered). This is active, LLM-driven consolidation that mutates the store on ingest, preventing duplicates and stale facts. In mem0g a dedicated conflict-detection step flags existing relationships that conflict with an incoming one, and an LLM update-resolver marks the old edge invalid (soft delete) instead of removing it, so contradictions are resolved while history is retained. The v3 OSS rewrite explicitly abandons this: "single-pass ADD-only, one LLM call, no UPDATE/DELETE; memories accumulate, nothing is overwritten" — pushing conflict handling to retrieval/temporal ranking instead.
- **Embeddings:** Dense embeddings of memory/fact text are the primary retrieval signal, stored in a pluggable vector store. mem0g additionally embeds entity nodes and encodes whole relationship triplets as vectors so queries can be matched against triplet encodings (semantic triplet retrieval). Embedding model is configurable (OpenAI, HuggingFace/sentence-transformers, Ollama, etc.). v3 OSS adds a separate entity embedding collection used for entity-match boosting, and fuses semantic + BM25 keyword + entity-match signals.
- **Retrieval:** Plain mem0: embed the query, cosine top-k over the memory vector store, return memories plus conversation summary and recent-message window. mem0g: dual strategy — (1) entity-centric search that locates query entities then traverses their incoming/outgoing relationships in the graph, and (2) semantic triplet search that embeds the whole query and matches against triplet embeddings above a relevance threshold. Results are combined. There is no PageRank/community-summary step in mem0 itself (that's cognee/GraphRAG territory). v3 OSS: hybrid multi-signal fusion — semantic + BM25 + entity-match scored in parallel and merged into one score, plus time-aware ranking to pick the right dated instance. Retrieval relies on vector/graph lookup, not an LLM call at query time (the LLM is used at write time).
- **Storage backends:** Vector stores (abstracted VectorStore layer, many supported): Qdrant, Chroma, PGVector, Milvus, Pinecone, Weaviate, FAISS, Redis, Elasticsearch, MongoDB, Upstash Vector, Azure AI Search, Vertex AI Vector Search, Supabase, plus Langchain wrappers. Graph stores (classic mem0g, via enable_graph + graph_store config): Neo4j (primary/most-tested), Memgraph, Kuzu (embedded), Amazon Neptune, Apache AGE; FalkorDB community-requested. Note: the external graph store integration was removed from the open-source v3 codebase (PR #4805, Apr 14 2026) and replaced by a hosted built-in graph on the platform / an in-vector-store entity collection in OSS. So a current pip install of OSS v3 may not ship the Neo4j graph module described in the paper.
- **Relevance to project:** Directly informs the project's tag-drift/dedup decision. mem0's core thesis is the opposite of the project's "append + batch reconcile": mem0 reconciles synchronously at write time with an LLM (ADD/UPDATE/DELETE/NOOP) so the store is always consolidated, whereas the project appends nodes and reconciles taxonomy in batches. mem0's approach validates that an LLM can reliably resolve contradictions/duplicates given the candidate + its nearest neighbors — exactly the seed for the project's synonymy step — but it's a per-write LLM call (cost/latency) that the project's hash + embedding-synonymy-link layers are trying to avoid for the common case. mem0g's soft-delete-on-contradiction validates keeping a "static-ish" graph honest without destructive edits; the project's static graph has no invalidation path, which is a gap if facts can update (consider an `invalid`/superseded flag analogous to the project's `seen` flag). mem0g uses free-form LLM entity types + relation labels (no fixed ontology), which validates the project's free-form tags over cognee-style ontology — but mem0 has no tag-drift control, so the project's hash + embedding synonymy + batch taxonomy reconcile is a genuine improvement over mem0's uncontrolled label space. mem0 embeds summaries/facts as primary and entity strings secondarily — exactly matching the project's "summaries primary, tag/entity strings for synonymy." mem0 has NO PageRank or community-summary retrieval, so the project's Personalized-PageRank seed-and-spread + GraphRAG communities is a differentiator borrowed from cognee/GraphRAG, not mem0. The v3 OSS pivot to "ADD-only + entity-boost, drop the real graph" is a cautionary data point: a major framework decided a traversable graph wasn't worth it at scale — worth understanding why before over-investing in graph traversal at 200-node prototype scale.

**Notable techniques:**
- Write-time LLM reconciliation: extract facts, retrieve similar, then LLM picks ADD/UPDATE/DELETE/NOOP as structured tool calls — keeps the store deduplicated and non-contradictory at ingest
- Two-stage graph build: separate entity-extraction and relationship-generation LLM passes producing typed (src, relation, dst) triplets
- Soft-delete / invalidation of contradicted edges instead of physical deletion, enabling temporal reasoning and audit trails
- Dual graph retrieval: entity-centric traversal + whole-query-to-triplet semantic matching with a relevance threshold
- Rolling conversation summary + recent-message window fed into extraction for context
- v3: hybrid fusion of semantic + BM25 + entity-match scores with time-aware/dated-instance ranking
- v3: graph collapsed into a cheap entity-overlap retrieval boost rather than a separate traversable store (radical simplification trade-off)

**What to adopt:**
- LLM reconciliation as a final tie-breaker: keep the project's cheap hash + embedding-synonymy layers, but borrow mem0's pattern of handing a new fact + its top-k nearest existing nodes to the LLM to decide merge vs. new — use it selectively (only when embedding synonymy is ambiguous) to control cost
- Structured tool-call outputs for the merge decision (explicit ADD/UPDATE/MERGE/NOOP enum) rather than free-text, for reliable parsing
- Soft-delete/invalidation flag on edges/nodes for superseded facts (extend the existing `seen` debug flag into a real `valid`/`superseded_by` field) so the static graph can represent updates without losing history — a lightweight version of mem0g's obsolete-edge marking
- Two-stage extraction (entities first, then relationships among them) tends to yield cleaner triplets than asking for both at once — useful for the project's tag/entity/concept extraction from summaries
- Feed a rolling summary + recent context into extraction to disambiguate references — relevant if the project ingests sequential/linked documents
- Embedding entire relationship triplets (not just node strings) to enable semantic edge retrieval, complementing the project's summary-primary embeddings

**Pitfalls:**
- Per-write LLM reconciliation (ADD/UPDATE/DELETE/NOOP) is expensive and latency-heavy; mem0 itself abandoned it in v3 OSS — don't make it the default path for every node at 200-node scale, use the cheap layers first
- Version confusion: the widely-cited arxiv paper and most blog posts describe the classic mem0g (Neo4j graph + LLM reconciliation), but the current OSS v3 (Apr 2026, PR #4805) REMOVED the external graph and reconciliation. Don't assume a fresh `pip install` matches the paper — verify against the installed version
- mem0g's free-form LLM-generated entity types and relation labels drift badly with no normalization layer; this is precisely the failure mode the project's tag-drift control targets — do not copy mem0's uncontrolled label space
- DELETE based on LLM-judged contradiction can erase correct facts on a hallucinated conflict; mem0g mitigates with soft-delete — never hard-delete on a single LLM contradiction judgment
- mem0 has no PageRank/community retrieval — its graph retrieval is shallow (1-2 hop entity traversal + triplet match); don't look to mem0 for the project's seed-and-spread/community-summary design, look to GraphRAG/cognee/Graphiti instead
- The hosted platform's 'built-in graph' is closed/commercial — the open-source path to a real traversable graph is the now-removed legacy module, so adopting mem0's graph code means pinning an older version

### Graphiti (Zep)

**TL;DR:** A temporally-aware, real-time knowledge graph for agent memory: it ingests discrete "episodes," LLM-extracts entity/relationship triplets with bi-temporal validity windows, invalidates (never deletes) superseded facts, and answers queries with hybrid semantic+BM25+graph search and no LLM call at retrieval time.  
**License:** Apache-2.0 (graphiti-core, getzep/graphiti). Open-source core; Zep is the hosted commercial product built on top.

- **Architecture:** Ingestion is episode-centric: each unit of input (a message, a JSON doc, raw text) becomes an immutable Episode node — a non-lossy ground-truth store. add_episode runs three sequential LLM stages: (1) extract_nodes / extract_edges pull entities and relationship triplets via structured (Pydantic) output, using the current episode plus the last n=4 episodes as context and a "reflexion" self-critique pass to reduce hallucination/missed entities; (2) resolve_extracted_nodes / resolve_extracted_edges dedup against the existing graph; (3) contradiction detection invalidates conflicting prior edges. The graph is a three-tier hierarchy: Episode subgraph (raw events) -> Semantic Entity subgraph (extracted entities + fact edges) -> Community subgraph (clusters with rolled-up summaries). Every derived fact links back to the episode(s) it came from. Updates are incremental — no full graph recomputation — which is the core design goal vs batch GraphRAG.
- **Graph model:** Node types: EpisodicNode (raw input, carries the source event timestamp), EntityNode (people/products/concepts, each with an LLM-maintained evolving summary and a name embedding), and CommunityNode (cluster summary). Edges are first-class EntityEdge objects storing a natural-language "fact" string plus the bi-temporal quad. Tags/entities are NOT free-form labels — they are full nodes; relation types are either generic (MENTIONS, RELATES_TO) or developer-constrained via custom Pydantic entity/edge types (an optional ontology). Temporal/versioning is bi-temporal at the edge level: facts are versioned by validity windows, old versions retained.
- **Extraction:** LLM-driven, requires a Structured-Output-capable model (OpenAI/Anthropic/Gemini recommended). extract_nodes prompt pulls entities (speaker auto-extracted as an entity in chat mode); a reflexion/reflection prompt re-examines the extraction to catch missed entities and minimize hallucination. extract_edges then extracts relationship triplets between the already-identified entities, optionally guided by supplied relation-type descriptions (e.g. LOVES, IS_FRIENDS_WITH) and custom edge Pydantic schemas. Edges also get LLM-extracted temporal info (valid_at / invalid_at) parsed from text. Concurrency across these LLM calls is bounded by SEMAPHORE_LIMIT (default 10) to dodge 429s.
- **Dedup / conflict:** Node dedup (entity resolution): embed the new entity name (1024-d), run dual hybrid candidate search (cosine over entity-name embeddings + full-text/BM25 over names & summaries), then an LLM entity-resolution prompt judges which candidates are the same entity given episode context; on merge it regenerates a unified name and summary. Newer versions add entropy-gated fuzzy matching — approximate Shannon entropy over normalized name characters gates fuzzy string matching so low-entropy/short names aren't spuriously merged. Edge dedup mirrors this but the candidate set is constrained to edges between the SAME entity pair (big complexity reduction). Conflict/update handling is the differentiator: instead of mutate/delete, an LLM compares a new edge to semantically related existing edges; on a temporally-overlapping contradiction it invalidates the old edge by setting its t_invalid to the new edge's t_valid. History is preserved and queryable.
- **Embeddings:** Entity names embedded to 1024-d vectors; edge "fact" strings and community names/summaries also embedded for cosine search. The Zep paper used BAAI BGE-m3 for both embedding and cross-encoder reranking. The open-source library defaults to OpenAI embeddings but pluggably supports Voyage AI, Google Gemini, Azure, and — relevant here — Sentence Transformers for fully local embedding. Vectors are stored as node/edge properties inside the graph DB (no separate vector store required); BM25 uses the graph DB's native full-text index (Neo4j/Lucene).
- **Retrieval:** No LLM at query time. Three parallel search primitives over the indexed graph: cosine semantic search (over entity, edge-fact, and community embeddings), BM25 full-text (Neo4j Lucene), and breadth-first n-hop graph traversal. Results are fused/reranked by a configurable reranker: Reciprocal Rank Fusion (RRF, default fast), Maximal Marginal Relevance (MMR) for diversity, node-distance reranking (graph distance from a centroid node, e.g. the current user), episode-mention frequency reranking, or an optional cross-encoder LLM reranker (slowest, only reranking — still no generation). Retrieval returns text context (fact strings, entity summaries, optionally community summaries) that the calling agent injects into its own prompt. Configurable "search recipes" bundle a primitive set + reranker for common patterns.
- **Storage backends:** Graph + vectors + full-text all live in one graph DB. Supported: Neo4j 5.26 (primary), FalkorDB, Amazon Neptune (Database or Analytics, with Amazon OpenSearch Serverless as the full-text backend), and Kuzu (now deprecated). Embeddings stored inline as properties; BM25 via the DB's native text index. No NetworkX/SQLite path — it assumes a server graph DB.
- **Relevance to project:** Strong architectural sibling but different on several core bets, so it's a good validator/challenger. (1) Bi-temporal edges + invalidation vs your STATIC append+reconcile graph: this is the biggest challenge. Your pipeline appends and reconciles tags/taxonomy but has no notion of facts going stale or contradicting. For a Wikipedia corpus at ~200 nodes this is probably fine (Wikipedia facts are relatively stable, and you ingest snapshots not a changing event stream), so you can justifiably skip bi-temporality — but borrow the cheap version: keep a per-edge 'superseded_by' / valid flag so a later ingest can soft-invalidate rather than mutate, mirroring your existing 'seen' debug flag. (2) Extraction shape: graphiti extracts entities/edges directly from raw text with a reflexion pass; you extract tags/entities from an LLM SUMMARY first. Summary-first is cheaper and denoises, but you lose the episode-as-provenance link graphiti prizes — keep a back-pointer from every tag/entity to the source node+summary so you can audit and re-extract. (3) Dedup: graphiti's layered cosine + BM25 + entropy-gated fuzzy + LLM-resolution maps almost exactly onto your layered tag-drift control (hash + embedding synonymy + batch reconcile) — strong validation. Their entropy gate specifically addresses a failure mode you'll hit: short tags like "AI" or "US" being fuzzy-merged wrongly. (4) Retrieval: graphiti's no-LLM-at-query-time + RRF/MMR/node-distance reranking validates your PPR seed-and-spread (both avoid query-time LLM); consider adding node-distance/MMR reranking on top of PPR scores. (5) Communities: their label-propagation + map-reduce community summaries are exactly your GraphRAG-style community summaries — confirms that design; label propagation is cheaper than Leiden and incremental, worth copying. (6) Backends: graphiti rejects your NetworkX+SQLite stack (needs Neo4j/FalkorDB) — at 200 nodes NetworkX is fine and gives you free PPR (graphiti has no PageRank), so this is a point where your prototype choice is actually better-suited than theirs.

**Notable techniques:**
- Bi-temporal edge model: t_created/t_expired (system/transaction time) plus t_valid/t_invalid (real-world validity) — enables 'what was true as of date X' queries
- Edge invalidation instead of deletion: contradictions set t_invalid = invalidating edge's t_valid, preserving full fact history
- Episode-as-immutable-provenance: every fact traces back to source episodes (auditability / non-lossy)
- Reflexion self-critique pass during entity extraction to reduce hallucination and improve recall
- Entropy-gated fuzzy entity matching to avoid bad merges on short/low-entropy names
- Edge dedup scoped to same entity-pair to cut search cost
- Label-propagation (not Leiden) community detection with incremental plurality-vote assignment of new nodes, plus map-reduce community summaries
- Pluggable rerankers (RRF / MMR / node-distance / episode-mentions / cross-encoder) decoupled from the search primitives
- No-LLM-at-query-time retrieval for low latency
- Custom Pydantic entity/edge types for optional constrained ontology

**What to adopt:**
- Entropy-gated fuzzy matching for tag/entity dedup — guard short/low-entropy tag strings from being merged by embedding/fuzzy similarity alone
- Constrain edge/synonymy dedup search to candidates sharing an entity-pair (or same tag namespace) to cut reconcile cost
- Reflexion self-critique pass after tag/entity extraction from the summary to catch missed concepts cheaply (one extra Haiku call)
- Keep an explicit provenance back-pointer from every tag/entity/edge to the source node + summary + episode, graphiti-style, for audit and re-extraction
- Add a lightweight soft-invalidation flag on edges (alongside your 'seen' flag) so re-ingestion can supersede instead of mutate — a poor-man's bi-temporal model without the full quad
- Layer node-distance and MMR reranking on top of PPR scores for diversity and query-anchored relevance
- Use label-propagation for community assignment (incremental, cheap) and map-reduce summaries for GraphRAG community nodes
- Store summary embeddings as primary retrieval vectors and tag/entity-name embeddings only for synonymy — matches graphiti's split of edge-fact vs entity-name embeddings
- Bound LLM concurrency with a semaphore (their SEMAPHORE_LIMIT) since Haiku ingestion will fan out per node

**Pitfalls:**
- LLM-at-ingest is expensive and serial-ish: every episode triggers multiple LLM calls (extract nodes, reflexion, extract edges, entity resolution, edge dedup, contradiction check) — ingestion latency/cost is the known weak point; your summary-first approach is lighter but watch the per-node call count
- Graphiti's relations are often generic (MENTIONS/RELATES_TO) and 'lighter on semantic depth' per cognee's benchmark — free-form/auto relation typing tends to collapse to vague edges; your explicit tag/concept extraction may actually be richer if you constrain relation vocabulary
- No PageRank/PPR in graphiti — its traversal is plain BFS n-hop + reranking; don't assume you can lift a traversal algorithm from it, your PPR is your own
- Assumes a server graph DB (Neo4j/FalkorDB); there is no NetworkX/SQLite story, so its storage code is not reusable for your prototype
- Bi-temporal correctness depends on the LLM correctly parsing valid_at/invalid_at from text and on the contradiction-detection prompt firing — mis-parsed dates silently corrupt the time model; if you adopt soft-invalidation, keep it conservative
- Kuzu backend is deprecated — don't build on it
- Community assignment by neighbor plurality (label propagation) is unstable on small/sparse graphs — at ~200 nodes communities may be noisy; validate before relying on community summaries
- Entity-summary regeneration on every merge can drift the summary over many merges (telephone-game effect) — pin summaries to source provenance to allow recompute
